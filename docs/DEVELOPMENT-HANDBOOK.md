# 开发手册（项目必读）

> 本文件是本项目的**开发方法论宪法**。任何对引擎、patch、配置、性能的改动，先读本文件再动手。
> 它记录的每一条都是从实际返工中提炼的，不是理论建议。
> 配套：`docs/DEPLOY-v075-NOTES.md`（部署坑与脚本底稿）、`docs/performance/`（性能台账）。

---

## 0. 总纲

**我方基线是已经过生产验证的最佳版本。社区不一定更好。**

引入社区改动的唯一目的是**在我方优化之上再吃到增量收益**。
因此：**没有可验证的增量时，基线就是最优解，不动它就是正确决策。**
「上游更新了所以我们该跟上」不是理由。

---

## 1. 方向：把社区特性摘到我方基线上，而不是把我方 patch 搬上游

| 错误方向 | 正确方向 |
|---|---|
| 以上游新版本为底，把我方 52 个 patch 往上搬 | **以我方基线为底**，把社区特性逐个摘进来 |
| 大爆炸换底，一次改动上万行 | 每次只动一个特性，通常几十行 |
| 总账持平时无法归因，只能到处找「丢了什么」 | 每一步都能独立归因 |
| 我方优势在搬运中可能被稀释 | 我方优势天然保持不动 |

**基线树的构造**（已验证可精确复现）：
```bash
cd <upstream-clone>
git worktree add -f --detach /tmp/tf-base <我方pin>
cd /tmp/tf-base
for f in <repo>/zig/patches/*.patch; do git apply --3way "$f"; done
# 期望：52/52 干净落地，零冲突。任何冲突都说明 pin 或 patch 集不对，先查明再动。
```

## 2. 吸星大法：每个社区特性的六步流程

**顺序不可颠倒，尤其不可跳过第 1、2 步直接构建运行。**

1. **读代码**。看这个 MR/commit 到底改了什么、**为什么**改、**怎么**实现的。
   读 commit message 的正文（作者通常写明了动机与实测数字），再读 diff 本体。
2. **判断对我方是否有益**。结合我方的真实工况（≤4 路并发、KV 分片开、内存红线、
   EAQ v1.1 混合包、我方 kit）。**很多社区改动修的是我方根本不存在的坑。**
   无益就明确跳过并写明理由，不要「先合了再说」。
3. **定吸收方式**。三选一：
   - **cherry-pick**：改动小、与我方结构兼容；
   - **重写**：上游实现依赖我方没有的结构，或我方有更优路径；
   - **启发**：不取它的代码，只取它的思路，做一个更适合我方的实现。
4. **同场 A/B**。见 §3。必须同场重测对照臂。
5. **确认收益且与预期相符**。收益方向对但量级差很多，说明机制理解有误，**回去查因，不要收下**。
6. **并入基线，抬高地板**。commit + 更新台账。然后看下一个，重复 1–6。

### 2.1 判断「是否有益」的实战样例

| 社区改动 | 它解决的问题 | 我方判定 |
|---|---|---|
| `share_check` | `TF_FILL_CHUNKS` 开着时独占 pass 也被切碎，8K 慢 2.2% | **跳过**：我方未设 `TF_FILL_CHUNKS`，pass 本就整段跑，无此坑 |
| `TF_DS_PASS_FROM` | 8192 以上用 4096 行 pass 才划算 | 需 4096 行 → arena 6144 MiB → **撞内存红线**，不能单独吸收 |
| `TF_DS_PROMPT_ALIAS` | prompt scratch 归并省内存 | 本身不提速，但**恰好腾出上一条所需的内存** |

**关键教训：候选之间存在耦合。** 上表后两条单看都会得出「没用」或「开不起」的错误结论，
合起来才是一条有明确预期收益的路径。**审候选时要看它们能不能互相解锁。**

### 2.2 「社区新增提交数」是假象，必须按内容核实

`git log <我方pin>..<上游tag>` 的数量**严重高估**真实增量：
同一改动常经由另一条分支线早已进入我方 pin，合并拓扑仍把它算成「新增」。

**正确做法：按符号/env 名在我方基线树里 grep，确认内容是否已在位。**
```bash
cd /tmp/tf-base && grep -rn "TF_DS_XXX" zig/src | head
```
实测教训：某次列出 2211 个「新增」提交，其中两个标着 `perf(dsv41)` 的核心开关
（`TF_DS_NO_COPIES`、`TF_DS_SOLO_OVERHEAD`）**我方基线早就有了**。
先 grep 30 秒就能知道，盲目 apply 会绕一大圈。

### 2.3 候选筛选的六道闸（先过闸，再读码）

一个提交标题再对路，先过这六道闸，**过半候选死在这里**：

| 闸 | 判据 | 本轮实例 |
|---|---|---|
| **后端** | Metal ≠ CUDA | `dd7c516a4`「每权重一窗口只读一次」只改 `kernels/metal/` |
| **家族** | Nemotron / lfm2 / glm ≠ dsv41 | `db7364e63` loads-in-flight 只改 `nemotron_*.cu` |
| **拓扑** | TP4 / four nodes ≠ 我方 TP2 | `c7aef7339` parity 专家切分明写 four nodes |
| **量化** | EXLR8 / NVFP4 ≠ 我方 exl3-2.9bpw | `51426b8e6` EXLR8 trellis |
| **规模** | >4 路 / 64 行轮 ≠ 我方 ≤4 路 | `06afb468e`、`c79c714ca`、`d27e3d422` |
| **可改性** | **当前树无源码 ≠ 上游无源码** | **E-SELF-02：cubin 的源码在另一条线的历史里，查全 ref 才找到** |

**查法**：`git diff-tree --no-commit-id --name-only -r <hash>` 看改的是哪些文件——
文件路径直接暴露后端与家族，比读标题可靠。
共享目录（如 `src/cuda/`）还须再确认**我方家族是否真的 import 它**：
`dc9d8bb6c` 改共享 `cuda/norms.zig`，但 dsv41 无该 import，等于不适用。

**第六道「可改性闸」的查法（自研尤其必过）**：
按 mangled 名反查我方家族真正调用哪个内核，再确认那个内核**有没有源码**：

```bash
grep -rn "_ZN" zig/src/families/dsv41/*.zig      # 我方真正的内核名
grep -rln "<kernel_symbol>" --include=*.cu .      # 0 命中 ⇒ 可能是预编译件
```

**我方 exl3 专家/线性路径以 kit 预编译 cubin 分发**（`kit/cubins/*.cubin`，kit 不发 .cu），
但**源码在上游公开**——`c99083245` 的 `src/tensorfold/cuda/exl3/experts_grouped.cuh`（2283 行）
+ `experts_cb2.cu`（14 行，自包含）。**「当前 worktree 里没有」不等于「拿不到」。**

**判「无源码」前必须查全**（E-SELF-02 就是漏了这步而误判）：

```bash
git log --all --oneline --name-only --diff-filter=AM -- "*<关键文件名>*"   # 全 ref 全历史
git ls-tree -r --name-only <候选commit> | grep -i <关键词>                # 该版路径
```

注意源码可能在**另一条线**（Python 线 `src/tensorfold/` vs Zig 线 `zig/`），
且同名文件的**不同版本模板参数个数不同**（6 参数 `grouped_kernel` vs 8 参数 `grouped_rows_kernel`），
**必须用签名与实例化配置对上我方 cubin 才算找到对的那份**。

**过闸后剩下的，若代码不适用但机制对路，归入「启发自研」而非丢弃**（见 §2 第三步）。

### 2.3.1 启发自研前必做「机制同构核查」

不是问「我方有没有这个 commit」，而是问
**「我方 kernel 有没有这个机制、是什么形式、孰强孰弱」**。

**顺序不可颠倒：① 先测量定位靶子大小 → ② 再读码核实机制是否已存在 → ③ 才谈实现。**

实测教训（E-SELF-01）：打算把 Nemotron 的「让 load 保持在飞行中」移植到 dsv41。
- 第①步 profiling 发现：该改法的靶子 router/topk 在我方 decode 里只占 **m_rt 629.9 µs / 轮 ≈ 整轮 2%**，
  而 **moe 占 12909 µs（stretch 口径 78.2%）**。**靶子选错了。**
- 第②步读码发现：我方 `lane_gemv.cu` 是 `gemv_kernel<64,64,8>`，
  `cp.async.cg.shared.global` 16B，主循环前灌 7 级、循环内提前 7 级发射；
  `experts.cuh` / `qmm_group.cu`（8 级）同样。**机制早已存在，且是比上游寄存器 staging 更强的多级软件流水。**

**两步都在写任何代码之前完成，避免了一次实现已有功能的无效开发。**

### 2.3.2 decode 分段 profiling 的正确取法

`RANK1_PROFILE=1` + `TF_DS_CLOCK_MARKS=1` → 跑探针 → **停服**（profile 在退出时才打印）。
- **容器会被停服流程重建，`docker logs` 拿不到**。去 worker 的
  `~/.cache/dsv41-tensorfold/logs/*rank1.log.gz` **归档**里 `zgrep round_clock_us`。
- `CLOCK_MARKS=1` 在 graph 内也打点，**打断 PDL 链、绝对值偏大**（实测 N=1 58.621 vs 基线 59.1）。
  **只用相对占比，绝对值不得当基线。**
- stretch 总段（`moe`/`attn`/…）与细标记（`a_*`/`sh_*`）是两套口径，**不可相加**。
- `m_gu`/`m_x` 计数为 0 属正常：那是 TP4 2D MoE 的标记。

### 2.4 上游的「无收益」结论不可跨配置外推

上游 commit body 里的实测结论绑定**它自己的硬件与拓扑**。
例：`28dbfe128` 写 "the settings swept on real one-stream decoding move nothing past noise"，
但那套 L2 prefetch budget 与配速是在 **TP4** 上调的，**每 rank 权重字节数只有我方 TP2 的一半**。
差异落在决定性维度上时，其零结论对我方无效，须自行重扫。

反之亦然：**上游的正收益同样不可直接外推**（参见 B 步 `TF_DS_PASS_FROM` 的 +5.6% 实为
hybrid vs 4096-everywhere，不是我方起点）。**两个方向都要按我方真实起点重算。**

## 3. 测量纪律（最重要，违反它会让全部结论作废）

### 3.1 任何 A/B 必须同场重测对照臂

**禁止复用历史基线数值做单次增量判决。**

本机同日状态漂移可达 **1%**，与待测增量同量级。
实际事故：3b 端口后用今日数据对比历史基线，得出「−1% 回退」，
据此追查「丢了哪个 patch」耗费大量工时；同场重测基线后发现
**3b 实际是 +0.11% / +0.36%，根本没有回退**。

- 历史基线**只能**用于长期趋势观察。
- 每个 A/B 批次内，对照臂与实验臂必须**同一时段、同一探针、同一重启流程**测出。
- 报告里必须写明对照臂是本次实测还是历史值。

### 3.2 口径

- prefill 一律用 **`未缓存输入token / server.prefill_seconds`**，不用端到端时间。
- decode 取 `decode_tok_s`，多 rep 时**除首次外取中位**（首次含预热）。
- 并发看**聚合吞吐**，同时记录每流值。
- 记录 `tok/轮` 与 `接受率`：decode = tok/轮 × 轮/秒，**两者必须分开看**才能归因。
  实例：`SOLO_OVERHEAD=1` 使 tok/轮 2.0157→2.0317 但接受率 0.5646→0.5417，净亏 2.22%。
  只看吞吐会以为是噪声，看分解才知道是「草稿更深但接受更少」。

### 3.3 禁止比例连乘推收益

不得用「A 比 B 快 x%，B 比 C 快 y%，所以 A 比 C 快 (1+x)(1+y)」代替实测。
每一格都要实测。2×2 表缺哪一格就补测哪一格。

### 3.4 探针选择偏差：必须补对抗性负载

**一个开关在合成探针上为正，不等于它在真实负载上为正。**

凡是改动**投机 / 复制 / 草稿机制**的开关，除了常规探针，**必须再跑一个最大化该机制贡献的
对抗性负载**，两个场景都过才可收下。

实际事故（E-ABS-02）：`TF_DS_NO_COPIES=1` 关闭 suffix-lookup 复制窗口。
- 常规探针（47 token 短 prompt → 生成 512 token，几乎无重复）：交替 A/B/A/B **四次配对全正**，
  N=1 +0.30%/+0.35%，N=4 +0.74%/+0.39%，看起来是真实小收益。
- 对抗探针（长重复文本 + 要求逐字复述）：**N=1 −4.87% / −4.46%**，
  tok/轮 从 3.5068 掉到 3.3247 —— 复制窗口本来在实打实产 token。

**常规短探针恰好是该开关的最有利情况。** 真实 agent 负载（工具输出回放、文件引用、
代码编辑、reasoning 重放）充满重复，对抗场景才具代表性。若只看常规探针，
就会把 −4.7% 的真实退化当成 +0.6% 的收益锁进基线。

**推论**：收益方向随负载翻转的开关，不得设为全局默认。

### 3.5 小效应必须交替多轮

待测效应 ≲1% 时，单次 A→B 抗不住漂移。用 **A/B/A/B 交替**，
看**每一对配对差是否同向**，并比较效应量与同配置内散布的比值。
符号一致性比单次幅度更有说服力。

## 4. 内存红线与操作纪律

- **生产 head 多路最小空闲 4.8 GiB 是硬红线。** 空载单流的富余不代表生产富余。
- 任何构建前：**先停服**，断言 `MemAvailable > 100 GiB`。
- **绝不并行跑两个引擎实例。**
- 不得下调 `TENSORFOLD_MEMORY_RESERVE_GIB`。
- **arena 由编译期常量定容**（`model.zig` 的 `prompt.Chunk.init(..., chunk_rows, ...)`）。
  `TF_DS_PASS_ROWS` 只限制实际 pass 长度，**改不动 arena**。要省 arena 必须改编译期常量。
- 用户不在场时爆内存需人工断电、可能十几小时无法恢复。**宁可少测一轮，不可越线。**

### 4.1 停服/恢复标准流程

```bash
systemctl --user stop dsv41-tensorfold.service
sleep 8
# 改配置
systemctl --user reset-failed dsv41-tensorfold.service   # StartLimitBurst=3/30min
systemctl --user start dsv41-tensorfold.service
# 轮询 /health 至 200；就绪约 50–95 s（视镜像而定）
```

## 5. 端口与合并的工程陷阱

1. **必须 `git apply --3way`**，直接 `git apply` 会大面积失败。
2. **逐 patch 解完冲突并 `git add -A` 后，才能落下一个。**
   否则报 `does not exist in index`，后续 patch 整体失败、新文件不生成。
   （此坑本人踩过两次，写在这里就是为了不再有第三次。）
3. **改枚举编号要改全部三处**：枚举定义、对应模块的 `kind` 常量、
   **字节→枚举的解码 switch**。漏第三处 → 对端 `BadFrame` → 本端 `PairBroken` → 进程退出。
4. **`SafeAllocator leaked` 是错误后的清理噪声，是果不是因。** 排错时先找首个真实错误。
5. **上游可能拆分了我方单一常量的语义**。例：我方 `chunk_rows=2048` 被上游拆成
   `chunk_rows=4096`（pass 大小）+ `resume_rows=2048`（保留态网格）。
   我方按块粒度做保留态判定的地方，对应的是 `resume_rows`，断言要写对。
6. **上游重命名了我方 env**：我方 `TF_DS_POOL` ↔ 上游 `TF_DS_WINDOW`；
   我方 `TF_DS_WINDOW` ↔ 上游 `--context`。端口时要做映射，不能照抄名字。
7. **自包含新文件可单独提取**，不必端口整个大 patch。
   例：KV 分片依赖的 `rank_wire.zig`/`fingerprint.zig` 由 8699 行的 spill patch 新建，
   但两者自包含，单独提取即可，冲突从 71 块降到 17 块。
8. 解冲突原则：**上游演进处取上游，我方独有功能加回去**；
   theirs 混入的未端口依赖只挑需要的行；上游移动了符号则改挂到上游模块。

## 6. 如何确认一个特性「真的生效」

**不能只看「服务起来了」。必须拿到直接证据。**

| 证据类型 | 做法 |
|---|---|
| env 真进了容器 | `docker exec <容器> env \| grep TF_DS_XXX` |
| 启动日志实证 | 抓 `pool ... positions` / `arena ... MiB used` / 特性自己的 info 行 |
| 符号真在镜像里 | `strings <二进制> \| grep <kernel符号>` |
| 没有静默回退 | 抓该特性的 warn 行（例：ring kernel 缺失会 warn 并退回 NCCL） |
| 内存数对得上 | 分片开：532 MiB/rank；关：893 MiB 复制 |

**注意日志归档时机**：`*.log.gz` 是 stop 时归档的**上一次**运行。
看当前运行要用 `journalctl --user -u dsv41-tensorfold.service`，否则会拿旧数据当新数据。

**遥测缺口 ≠ 功能缺陷**：`/health` 某字段为 null 可能只是遥测链路没打通，
功能本身已由日志与内存数证实生效。两者要分开陈述，不可互相推断。

### 6.1 env 旋钮必须先过我方启动脚本的白名单

**上游能读的 env，我方部署不一定送得进容器。** `start.sh:291` 只直通
`^(TENSORFOLD|TF_DS|TF_SPILL|TF_FILL)_` 前缀，且另有排除表与 port 映射表。

两个实测陷阱：
- **前缀不匹配**：`TF_EXL3_L2_DELAY_NS` / `TF_EXL3_L2_RATE_GBPS` 属 `TF_EXL3_`，
  **一个都进不去**。不查就测，等于连测两臂空开关还得出一堆「噪声内」的假数据。
- **被 port 映射接管**：`TF_DS_L2_PREFETCH` 在排除表里，由 `PREFETCH` 经
  `start.sh:339` 注入。**直接 `export TF_DS_L2_PREFETCH=0` 无效，必须改 `PREFETCH=0`。**

**纪律：每吸收一个带旋钮的特性，逐个旋钮在容器里 `env | grep` 核验取值，
而不是只核验其中一个。** 扫描类实验尤其致命——某一臂没生效会伪装成「该参数不敏感」。

## 7. 记录与归档纪律

- **Git 仓库是本项目唯一标准。** Spark 上的项目目录不是 git 仓库，改动须 scp 同步回来。
- **实验只增不改**：结论被推翻时，**原文保留 + 追加「更正批注」**，不删原文。
  作废的推算要显式写明「该推算作废」及原因。
- **写前先读**：任何要写入的目录先 Read/Grep，避免覆盖既有权威产物。
- **review 后 commit**；commit 前扫描敏感串，hits 必须为 0。
- **>1 min 的构建/实测先报预计时长。**
- 每个实验建 `runs/forge-<YYYYMMDD>-<主题>/`，含 `REPORT.md` + `raw/` 原始数据。
- 长等待要给可见进度，不要静默数分钟。

### 7.1 判决台账模板

每个候选特性都要留下这样一行：

| 字段 | 内容 |
|---|---|
| 社区坐标 | commit hash + 标题 |
| 做什么/为什么/怎么做 | 读代码后的三句话 |

### 7.3 「有机制」≠「机制够用」

判断某优化是否已在位，不能只问「有没有这个机制」，还要问「**它的量够不够**」。

实例：我方专家 kernel 已有 cp.async **7–8 级**软件流水（形式强于上游的寄存器 staging），
但**实测 Occupancy 中位仅 17%**（`down` 255 regs/thread、128 threads/block ⇒ 8/48 warps），
**驻留 warp 太少 ⇒ 总在飞请求数仍不足以盖住延迟**。
**「有流水」不等于「在飞请求够多」。** 只看到前者就判「无实施空间」是错的。

> **【E-SELF-02 更正】** 上段「7–8 级 cp.async」读的是 `lane_gemv.cu` / `experts.cuh` /
> `qmm_group.cu`，**这些属于 Nemotron 家族，我方 dsv41 不调用**。我方 exl3 内核无源码，
> 流水结构未知。255 regs / 16.7% 那部分**已从二进制核实为真**
> （`tf_exl3x::grouped_rows_kernel<2,8,4,1,2,16,2,false>`，REG:255、STACK:0）。

### 7.4 静态占用率必须从二进制读，且要列全同族变体

**不要沿用文档里的 regs 数字**，用工具实测：

```bash
bash tools/kernel-resusage.sh            # kit cubin(cuobjdump) + 引擎 kernel(nvcc -Xptxas -v)
```

**判据**：静态上界 = ⌊65536 / (regs × threads)⌋ blocks × (threads/32) warps / 48。
shared 与寄存器分别算，**取更紧的那个**才是真限制因子。

**两条本轮踩过的坑**：

1. **只筛一个实例化就下结论**。我曾只筛 decode 的 `grouped_cp_kernel`（128 regs），
   就宣称「255 不存在、E-DRAM-01 错了」——**错**。255 属于 prefill 的 `grouped_rows_kernel`。
   **同族变体必须全量列出再判决**（`raw/kit-exl3x-named-resusage.txt` 有 86 个）。
2. **把「当前树没有」当成「拿不到」**。cubin 无源码是真的，但**上游公开源码存在**，
   在另一条线的历史里（`c99083245`）。**判「不可实施」前必须查全上游所有 ref 与历史路径**
   （见 §2.3 第六道闸的查法）。这是本轮最贵的一个误判。
3. **静态占用率低 ≠ 抬高它有收益**。E-SELF-02 路 A 实测：两个变体都把 16.7% 抬到 25%，
   却分别 −0.92% / −2.38%。**占用率只是中间量，必须落到吞吐上判**；
   且要看清换占用率付的是什么代价（复用？字节？工作粒度？），三者代价不同。

### 7.5 构建成功判定：`grep BUILD_OK` 在 `set -x` 日志上是假阳性

`build-alias.sh` 带 `set -x`，日志会把 **`echo BUILD_OK` 这条命令原文**也记进去。
于是 `grep -c BUILD_OK` 在构建**尚未结束**时就返回 1。本轮据此提前拷贝二进制，
做出了一个**不含改动的镜像**，白跑一轮冒烟。

**正确判据**（任一）：

```bash
tail -1 ~/build-x.log            # 末行必须是 BUILD_OK 本身
# 或等后台任务真正结束再取产物
```

**并且产物要验内容，不验存在**：改动的日志串是否真在二进制里——

```bash
strings ~/build-x-out/bin/tf-dsv41-lanes | grep -c "<新日志的关键词>"
docker run --rm --entrypoint bash <派生镜像> -c "strings /opt/tensorfold/bin/tf-dsv41-lanes | grep -c '<关键词>'"
```

**运行态还要看引擎自报**：env 到达容器 ≠ 改动生效。本轮靠引擎自己打的
`grouped_rows: … nt 4 pf 2` 才确认变体真被取用；只有 env 而无该行时，就是镜像里二进制不对。

> **同类假阳性第二次（E-SELF-04，2026-11-24）：空输入被判「一致」。**
> 位一致闸第一版报 `RESUSAGE_IDENTICAL` / `SASS_IDENTICAL`，但**所有比对文件都是 0 字节**——
> `diff` 两个空文件当然「相同」。根因是取数没匹配上：
> ① `cuobjdump -res-usage` 的 `Function` 行有**前导空格**，`awk '/^Function /'` 永不匹配（要用 `$1=="Function"`）；
> ② 从 res-usage 取的名字**带尾随冒号**（`Function NAME:`），传给 `-fun` 会 not found；
> ③ 传给 `-fun` 的 mangled 名不能截断签名后缀。
> **纪律：任何「一致 / 相同 / 通过」判定前，先对每个输入断言非空与数量下限**
> （`test -s`、`wc -l` 下限），空即 FAIL，绝不判 IDENTICAL。已写入
> `tools/cubin-roundtrip-gate.sh`、`tools/exl3-source-gate.sh`。

### 7.6 归因的三条硬规矩（E-SELF-03 立项时用户纠偏）

1. **「延迟受限」不是归因，是同义反复。** 说「慢是因为在等」等于没说。
   必须回答**谁在等谁、为什么供给跟不上消费**，并落到**代码结构或实测对照**上。
   合格的样子：「供给侧是 `__ldg` 单级寄存器缓冲，缓冲深度被累加器挤占 ⇒ 在飞请求不足」——
   这能被读代码验证，也能被同库另一条路径的对照证伪。
2. **用户已经做过的实验是最强证据，优先采用，不要自己重推。**
   用户主动降频且**升频实测无收益**——这一条直接排除算力侧、并正面支持延迟受限。
   我却把它当成「时钟可能是一条杠杆」，方向完全反了。**先问/先查已有实验，再设计新实验。**
3. **分母必须取官方口径，不能取工具报的极值。**
   nvidia-smi 报 `clocks.max.sm = 3003 MHz`，而 GB10 白皮书 Table 4 的
   **GPU boost clock 是 2.4 GHz**。用 3003 当分母算出「只跑到 74.5%」是**假缺口**。
   同理 L2：官方给了**容量 24 MiB**，没给带宽——「没测过」只对带宽成立，对容量不成立。
   **说「缺某个数」之前，先查官方规格书。**

### 7.7 没有单一短板时，要逐子系统归因

「三个饱和度同时都低」不是「没有瓶颈」，而是**每个子系统各被自己的依赖卡住**的表征。
此时正确动作是**把时间账逐行拆开，对每一行单独归因**，而不是去找一个统一解释。
我方 prefill 时间账里 **no-kernel 13.49% + collective 10.84% ≈ 四分之一窗口**，
这两块**至今完全未归因**，却长期被跳过——因为注意力都在最大的那一行（专家 core 38.38%）。
**最大的那一行不等于最该动的那一行**：core 归零且 idle 归零仍只 3604.90 tok/s，够不到 4000。

> **更正批注（E-SELF-05，2026-11-24）**：本节「no-kernel 13.49% 至今完全未归因」已部分过时。
> 该窗口 98.9% 集中在 4 个 >1ms 空隙，但 8 点 token 扫描的最小二乘判别显示
> `a·tok+c`（RMS 37.7ms）显著优于 `a·tok+b·chunks`（RMS 94.7ms，残差单调），
> **per-chunk 停顿不成立**；且采集用的是 `--cuda-graph-trace=graph`（图内 kernel 不展开），
> 空隙大概率是采集伪影，**「13.49% 可回收」这个前提已被否证**。原文保留以备追溯。
> 副产两个硬数据：边际吞吐 2243 tok/s、每请求固定成本 ≈275 ms（与 chunk 数无关，仍未归因）。

### 7.8 把「跑实验」提前到编译期：预筛闸

**GPU 时间是最贵的资源，编译时间不是。** 一个变体是否值得上机，很多问题在 `ptxas` 那一步就能回答：
寄存器是否顶到 255、是否出现 spill（`STACK>0`、SASS 里 `LDL`/`STL` 增量）、shared 是否超预算。

E-SELF-04 实测成本对比：

| 手段 | 耗时 | 能回答 |
|---|---:|---|
| 改 PTX 注入 directive 后 `ptxas` 重汇编 | **20 s** | 寄存器天花板、spill |
| 单编一个 `.cu` 成 cubin（`nvcc -cubin`，无需 pybind） | **56–66 s** | 任意形状变体的 REG/STACK/SHARED |
| 重建引擎 + 造镜像 + 重启 + A/B | **3–10 min + 数分钟** | 真实吞吐 |

**纪律：先编译期预筛，只让通过预筛的变体上机。** 路 B（压寄存器天花板）就是这样在 20 秒内被否决的
（REG 255→168/128 但 STACK 0→432/656 B），零 GPU 时间、零重启。

前置条件是**位一致闸**：先用未改动的源码/PTX 重建，与 kit cubin 比对
**指令逐条一致 + 资源账一致**，确认构建路径忠实，然后才敢相信改动的预筛结果。
注意判据**不是整文件字节一致**——`ptxas` 复现不了 kit 的 `.debug_*` 段（49.5 MB vs 11.7 MB），
整文件 sha256 只作记录。工具：`tools/cubin-roundtrip-gate.sh`、`tools/exl3-source-gate.sh`。

**换 cubin 不必重建引擎**：`TF_DS_KIT` 指向 kit 目录，`start.sh` 不校验 kit 哈希（只有 `prepare.sh` 校验），
`worker_files_check` 只查存在/可读/非空。worker 的 hf 卷是 head 的 NFS 只读共享，故 cubin 只需在 head 换一次。
**把基线与新变体的实例化编进同一个超集 cubin**，并验证基线内核仍逐条一致，
则 A/B 只是翻 env + 重启，臂间不换任何二进制。

### 7.9 沿「不变量线」做单因子实验

改形状时多个量会同时变，容易把结论归错。正确做法是**先找一条使若干量恒定的线，再沿线只让一个因子动**。

E-SELF-04b 的例子：down 的 `grouped_rows_kernel<CB,NT,W,PF,LO,HI,G,FOLD>` 里
`acc[G][NT][2][4]` = G·NT·8 个 fp32 寄存器。**沿 G·NT=16**：acc 恒 128、
程序总数 (N/(NT·16))·MG 恒定（MG=maxm/(16G)），于是看起来「只有解码冗余在动」。

**但这条线并不真的只有一个因子**：权重侧 ∝MG（随 G 下降），
**激活侧 X 读取 ∝ 列块数 N/(NT·16)（随 NT 下降而上升）**。
G=4/NT=4 同时动了两个因子，实测 −1.84%，无法据此归因。
必须再做 (G=1,NT=8) 与 (G=2,NT=4) 两格，把两个因子分开——**这才是可归因的实验设计**。

**教训：写下「唯一变化的是 X」时，要把所有随参数变化的量列全再核一遍**，
包括那些不在寄存器/shared 账里的（DRAM/L2 流量、barrier 次数、程序内固定开销）。

> **⚠️ 本节这个例子本身在 2026-11-25 复盘中被证明也是错的，正好当作反面教材。**
> ① `MG=ceil(maxm/(16G))` 里的 `maxm` 是**容量**不是活跃行数：真实重复倍数 ∈[1.16,2.13] 而非 64。
> ② 工作列表 `listLen(p,maxu,rows) ≈ p/rows + maxu` 有**每专家 padding 地板项**，
> 所以「程序数恒定」不成立，实际随 G 线性增长（32800→48160）。
> ③ 于是三个「单因子」测试格都同时改了程序数（×1.47~×2.00），**归因作废**。
> **两条新硬规矩**：
> **(a) 区分「容量上界」与「活跃量」**——grid 维度、`maxm`、`listLen` 全是容量，
> 活跃量要从 `p`、`ucount`、work list 有效项去定，或给出严格区间。
> **(b) 立项前先算 Amdahl**——本轮靶子 down 只占窗口 **12.59%**（归零上界 +14.4%），
> 相邻 gate/up 占 **25.79%** 却未被选。**灵敏度 ≠ 时间占比 ≠ 绑定约束。**

### 7.10 全局都不饱和是「上游单点卡住」的症状，不是并列结论

**用户原话**：「你可能后面两个没有满载是因为你前面有卡点呀……不能上来就看全局，觉得哪哪都不行，
然后也不知道具体谁不行。你得从问题的根源回溯，一点点往回查。」

**错的写法**：「DRAM 49.3%、SM Issue 36.2%、Tensor 37% 三项都不高 ⇒ 延迟受限」。
这是把症状清单当结论，且「延迟受限」是同义反复。

**对的做法**：从消费者 SM 起走**一条因果链**，每环都问「它饱和了吗」，直到命中饱和或结构串行的环节：

1. SM 发射率 → 不饱和则问 warp 卡在什么上
2. `smsp__average_warp_latency_issue_stalled_*`（**只用 `.pct` 归一，`.ratio` 是同值 ×100，混入会翻倍**）
   - `long_scoreboard` → 往上游查 L2、DRAM
   - `short_scoreboard` / `mio_throttle` → 片内 shared/shuffle 传送带
   - `barrier` → 块内最慢 warp（**注意：空转 warp 停在栅栏上会污染此项，见下**）
   - `wait` → 固定延迟依赖链
   - `math_pipe_throttle` / `not_selected` → 消费者已饱和
3. 各管线 `sm__pipe_*_cycles_active` + `lts__throughput` → 找真正接近 100% 的那个
4. `launch__occupancy_limit_{registers,shared_mem,warps,blocks}` → **让 ncu 直接点名限制资源**，别自己推

**三条配套硬规矩**：
- **stall 读数是全 warp 平均，含空转 warp。** 判 barrier 前必须做「补满有效 member」对照
  （ucount/组数/权重字节不变，只让死 warp 变活）。E-SELF-07 实测补满后 **+5.7% 变慢**，
  证明死 warp 不是负担、barrier 项被污染。
- **并发判据**：同会话内串行 N 次 vs N 流并发。若 ≈1.000×，说明 grid 已填满机器，
  卡的是每 SM 驻留 warp 数，**不是并发度**。event 必须真正 bracket 侧流
  （侧流 wait 起始事件 → 各侧流结束事件被默认流 wait），否则会量出荒谬的加速比。
- **零计数器不等于零事实**（GB10 陷阱复发）：`ldgsts_cache_access=0` 不能推出无 cp.async，
  源码 `:613/645` 明确对激活用了。**任何「某机制不存在」的断言必须有源码或第二条独立证据。**

### 7.11 驻留态禁止 replay ≠ 不能测 stall：离线单内核回放

E-DRAM-01 留下的「stall 原因拿不到」是**方法缺口，不是硬件限制**。
破法：stall reason 只需一个内核在真实形状下跑，**不需要整模型**。
一层专家权重 2.55 GB、总占用 2.96 GiB ⇒ replay 的 save/restore 完全安全。

**保真度闸（必须先过）**：离线单次耗时须与生产 trace **满格 grid** 的 call 中位对齐
（E-SELF-07：+2.2% / −4.5%），且 ncu 报出的 **mangled 名、grid、block 与生产逐字一致**。
**只取满格 grid 的 call**：混入尾块会把中位拉低（13.3761 → 10.687 就是这么错的）。

形状全部从 trace 的 grid 反解并互相验算；k2 从 checkpoint safetensors 头实测。
**API 细节**：wrapper 的 `B0/B1` 是 **k2 数组**，`TP0/TP1` 才是指针数组。
工具：`tools/probe-{build,layer,parse,pipes-parse}.py`、`tools/probe-{ncu,pipes,occ,sk-sweep}.sh`。

### 7.12 归因要判决，就得做「反向干预」；占用率不是杠杆的证据

**光有相关性读数不算定位。** E-SELF-07 拿到 `occupancy_limit_registers=2` 就把卡口写成
「寄存器钉住占用率」，这是**把限制资源当成了因果**。真判决要**反过来动它**：

- E-SELF-08 让 mma2 用**更多**寄存器（133 vs 106）、驻留**更少** block（1 vs 2）、
  占用率**腰斩**（15.55% vs 32.34%），结果**快 8.7%**。
- ⇒ 「占用率」这条因果被**直接否证**；寄存器的**主导角色是当权重暂存缓冲**，不是压占用率。
- ⇒ 也回溯解释了 E-SELF-02 整条「提占用率」路线全负：**方向本身错了**，不只是实现（spill）错了。

**硬规矩**：
1. **一个资源同时扮演多个角色时，必须设计能分离角色的干预**，不能靠读数猜主次。
2. **判决性证据 = 沿被指认的因果反向推，看结果是否随之反向。** 同向变化只是相关。
3. **多点交叉验证优先于单点幅度**：两个干预的占用率**一升一降**而带宽同向升，
   比任何单点 −9% 都更能排除「warp 数」这个候选。
4. **「字节数不变而时长变」是排除容量型卡口的判据**；反之「时长不变而字节数变」排除递货型。
5. **换实现往往同时改多个参数**（mma2 既改 cp.async 又改 `M2_COLS` 64→256）。
   落笔归因前先列全变化量（§7.9），并**优先选那个「自带劣势却仍变快」的检验点**
   ——down3 程序数多 7.5 倍仍快 8.8%，比 mma2 干净得多。
6. **新结构的代价要单独记账**：down3 的 barrier 从 6.6% 升到 25.6%（cp.async 环每级一栅栏），
   这是代价不是病；看净账，不要因为某项 stall 变大就否决。

工具：`tools/probe-mma2.py`、`probe-down3.py`、`probe-mma2-ncu.sh`、`probe-down3-ncu.sh`、
`probe-ab-parse.py`（统一解析器，**带标签参数**，避免 sed 改文件名导致存档列名错标）。

### 7.13 屋顶对比必须字节集齐全；ncu 的时长不能跨流水深度比

**两个当轮踩到的坑，都会直接把归因带偏：**

1. **屋顶内核必须搬「完整字节集」。** 首版纯读只搬权重 3.428 GiB，漏掉激活 staging 2.928 GiB（占 46%），
   却拿完整内核的耗时去比，得出「只到形状屋顶 64%」的错误结论。补齐后是 **1.43×（效率 70%）**。
   **规矩：写屋顶探针前，先把被测内核经手的每一类字节列全（权重/激活/输出/重复 staging），
   逐类核对字节数，再动手。** 重复 staging 尤其容易漏——激活被 9 个列块各搬一遍，
   DRAM miss 看不到它（L2 承接），只有 L2 请求口径才看得见。
2. **ncu 的 `gpu__time_duration` 在跨流水深度比较时失真。** 同一个 S=3 臂：ncu 报慢 11%，
   cuda event 报快 1.3%（min 值 22.43 vs 22.73，四配对三负）。原因是 replay 会膨胀访存延迟，
   浅流水受害更大。**规矩：时长一律以 event 为准（多臂交替 + 看 min 值），ncu 只取计数器。**
   跨臂算带宽时，分母用 event 时长，分子用 ncu 字节。

**配套两条（本轮验证有效）：**
- **一次编译出整个参数网格 + 环境变量选臂**，比每个变体重编一次快得多，且天然同进程同场 A/B。
  但**必须逐臂断言身份**：从 ncu 的 mangled 名核对模板实参等于请求值，否则环境变量没生效时
  会把噪声当成「各臂无差异」。
- **摘部件法（MODE 1/2/3）分离算术与 plumbing**：留解码去 MMA、留 MMA 去解码、两者全去。
  三者都只比完整快 ≤0.8 ms ⇒ 算术不是加数，6 ms 在搬运结构上。
  **⚠️ 更正（E-SELF-10）：后半句的推论作废。** 「逐个摘」在约束互相掩盖时会系统性低估联合成本，
  必须补齐 2×2 完整析因（见 §7.14）。正确分解是算术+同步 62.9% / staging 37.1%。
  **注意编译器会降级**：MODE 3 只用 `a[0]`，ldmatrix 被降成普通 shared 读（`ldsm=0`），
  这反而让 isolation 更干净，但**必须从计数器发现并说明**，不能声称「保留了 ldmatrix」。
- **摘同步是合法的「只计时探针」**：去掉 `__syncthreads()`/`cp_async_wait` 会引入竞态、结果不对，
  但**指令数与访存字节不变**，故时长有效。**必须同时报指令数与字节数证明没跳过工作**，
  并在源码与报告里标明「绝不可上线」。本轮据此否证了「栅栏门控发射」假设。
- **stall 首因会随干预迁移，别把「等待显现处」当成本源**：摘掉栅栏后 barrier 21.6→0.7%，
  但 short_scoreboard 4.4→21.1%、mio_throttle 0.9→8.9% —— 总时长几乎不变。
  **判据：摘掉某同步后若总时长不降，则该同步不是成本，只是依赖的显现位置。**
- **每 SM 共享的队列（MIO/LSU）不会因为加 block 而变多**：这解释了「占用率上去了却更慢」
  的一类现象。判断某资源是否 per-SM 共享，再决定加 block 有没有意义。
- **`sectors/request` 要按每 lane 字节数换算再判合并**：16 B/lane ⇒ 512 B/warp ⇒ **16 sectors 是满合并**。
  曾因把 17.64/8.45 当成「偏高」而误疑合并缺陷（E-SELF-07 遗留疑点，本轮结掉）。
- **编译器会把 `if (i < live)` 谓词化而非分支**，被守护的指令仍然发射并计入 `inst_executed`。
  核实办法：按「全发」算预测值与实测比对（本轮 ldsm 预测 76,677,120 与实测精确相等）。

### 7.14 摘部件必须做完整析因；屋顶的「带宽可达」不等于「布局可达」

**E-SELF-10 用一次真实重构 + 一次完整析因，换来四条硬规矩。**

1. **互相掩盖的约束，单独摘会系统性低估。** 摘算术 −0.726 ms、摘同步 −0.843 ms，
   两者一起摘 **−4.304 ms**（超加性 **2.74×**）。因为 stage 时间 ≈ `max(内存落地, 计算)`，
   两侧接近时摘掉任一个，另一个立刻完全暴露、继续封顶。
   **规矩：凡用「摘部件法」给成本占比，必须先补齐 2×2 完整析因（有/无 × 有/无），
   并报「条件效应」而不只是主效应。** 缺一个交互格，就会把联合成本几乎全部误记到没被摘的那一侧。
   本轮据此把「算术 11.2% / staging 88.8%」更正为「算术+同步 62.9% / staging 37.1%」。
2. **两侧成本接近 = 配平流水线 = 全局都不饱和的终点。** 算术 3.461 ms vs 同步 3.578 ms（差 3.4%）。
   配平下 DRAM 62% / Tensor 46% / SM 50% 同时不饱和是**结构性必然**，不是三个并列毛病，
   **也不再是「上游单点卡住」——两侧互为止点**。
   **规矩：沿因果链回溯到「两侧配平」就到底了，此时任何单侧优化收益都被另一侧封顶；
   要继续提升只能改变「每搬运字节的算术量」来打破配平，且收益上界由另一侧决定，禁止按字节比例连乘。**
3. **屋顶探针的带宽结论不可跨布局迁移。** 屋顶内核直取 L2 达 429 GB/s，据此推断「激活可绕过 shared」——
   实现出来**位一致但慢 3.27×**。因为 MMA 的 A fragment 天然是「每 lane 4 B、跨 8 行」，
   直取全局 ⇒ sectors/request 17.64→7.41、load 指令 15.2×、long_scoreboard 86.4%。
   **shared 往返是「布局变换器 + 延迟缓冲器」，不是浪费。**
   **规矩：拿屋顶当可行性依据前，先核对屋顶与被测内核的「每 lane 字节数 / 访问布局 / 指令粒度」是否同构；
   带宽承接得住 ≠ 布局承接得住。**
4. **手工推导的寄存器布局，用「位一致」当正确性闸。** MODE 7 只改操作数「怎么进寄存器」，
   不改数值与累加顺序 ⇒ 必须 `torch.equal` 为 True。闸过了才能把「慢」归因到性能而非算错。
   **规矩：语义等价的重构一律先过位一致闸，再看时长；只计时探针（故意竞态）要明确标注免检并禁止上线。**

**配套两条工程纪律（本轮踩到）：**
- **环境变量选臂的分支顺序会静默劫持实验。** `TF_PROBE_M2_S` 的分支排在 MODE 链之前，
  `S=3 MODE=6` 会命中**完整算术的 S=3 臂**。必须给先出现的分支加「其它选择器为默认值」的门控，
  并**逐臂用二进制 mangled 名断言实例存在**。本轮跑前拦下，否则整份判决都是假的。
- **`cuobjdump -res-usage` 输出的是 mangled 名**，形如
  `_ZN8tf_exl3x19grouped_mma2_kernelILi0ELi6ELi6ELi64ELi{S}ELi{MINB}ELi{MODE}ELi{KB}E…`。
  按 demangled 的 `<2, 6, 6, 64, …>` 形式 grep 会全部落空，**别把「grep 不到」当成「实例不存在」**。
  **不要假设运行时守护省下了指令。**

### 7.15 「利用率」的分母必须是可达屋顶；配置自报行不是身份证据

**E-COMM-01 用一次协议 A/B + 一次屋顶标定，换来五条硬规矩。**

1. **env 自报行 ≠ 生效证据。** `NCCL_PROTO set by environment to Simple` 只证明 env 到达进程。
   `NCCL_DEBUG_SUBSYS=INIT,ENV,TUNING` 打的 `Protocol | LL | LL128 | Simple |` 是**候选表头**，不是选择结果。
   真正的身份证据是**逐次决策行** `AllGather: <Bytes> Bytes -> Algo RING proto SIMPLE channel{Lo..Hi}={0..63}`。
   **并且必须按服务启动时刻分段归属** —— 一个跨越两臂的 `--since` 窗口会把两臂的行混在一起。
   同理：**内核符号名 ≠ 运行时协议**（`ncclDevKernel_AllGather_RING_LL` 的符号里带 LL，运行时却是 SIMPLE）。

2. **写「利用率 X%」前先问分母是不是可达屋顶。** 本轮把 14.19 GB/s 除以「双口 200 Gb/s = 50 GB/s」得 28.4%，
   看着有 3.5× 空间；实读 PCIe 协商是 **Gen5 ×4 两个域 = 31.51 GB/s**，而**实测可达峰值只有 18.9 GB/s**，
   生产已达孤立可达的 **92.2%** ⇒ 真实余量 1.085×。**线速、规格书理论值、工具极值都不是可达分母。**
   与 §7.6「分母取官方规格书不取工具极值」并列：**规格书用于物理上界，可达屋顶用于判断有无空间，两者都要报。**

3. **先找「与生产同形状、可与生产并存」的孤立 bench，再谈优化。** 镜像自带 `tf-dsv41-comm` 的 2048 行
   恰为 41,943,040 B = 生产主项尺寸（与决策行字节精确相等，互为交叉校验），显存仅 126 MB。
   它把 A/B 从「改配置 + 重启 + 等就绪」的 4 min/臂降到 **25 s/臂且不碰生产**。
   **这类工具的存在会把一整族候选的验证成本降一个量级，值得先花时间找。**

4. **「拆分绕过掉档」必须把落地代价一起测。** 带宽 >21 MB 掉档，拆 2 子 gather 纯发送 −16.8%，
   但拷回正确布局后 **+9.7% 更慢**。拷贝 722 µs 搬读+写 167.8 MB = **232.4 GB/s = DRAM 屋顶 94.4%**，
   已在屋顶、无压缩余地 ⇒ **只有消费端直读新布局才划算**。
   **D2D 拷贝的带宽必须按读+写双向计**：只按单向算会得 47.2% 屋顶，误判成「还有余地」，结论方向相反。

5. **同字节、不同 dtype/元素数的对照，能把「dtype 收益」变成「字节收益」。**
   20.972 MB 处 fp32(1024 行) 1150.8 µs vs bf16(2048 行) 1130.4 µs ⇒ **时间只由字节数决定**。
   于是 bf16 的实测收益**可无损迁移到 fp16**（同为 2 字节），而 fp16 尾数 10 位优于 bf16 的 8 位。
   **先证明「代价只依赖某个标量」，再在该标量上选最优方案** —— 比逐 dtype 试一遍更强。

**配套工程纪律**
- **正确性闸会抓到自己写的 bench。** 本轮 host 缓冲被上一轮 gather 下载结果覆盖，导致 f32 臂 rows≥128 全 `ok=false`
  （bf16 臂每次重建图案故通过）。**时间读数看起来完全正常。** 若只看时间就报数，整份判决都建立在一次未过闸的运行上。
  ⇒ **下载缓冲与图案缓冲必须分离**；§7.5「任何『一致/通过』判定前先断言输入非空」在此具体化。
- `socket(AF_INET, SOCK_STREAM, proto)` 第三参是**协议号**，写 1（ICMP）与 SOCK_STREAM 不兼容 ⇒ 返回 −1，
  表现为 `bind: Bad file descriptor`。用 0。
- 相对缩放（`new/base`）与绝对目标（`N × 孤立时长`）是两种不同的 Amdahl 行，**混用会让 saved 恒为 0**。
- **基线表必须标注「请求形状 + 测量工具 + 分母字段」，否则跨工具对比会凭空造出假回退。**
  E-COMM-01 核验恢复时用 `bench.py`（2048/8192/32768）对基线表的 2084.42 / 59.265 / 107.621，
  得 −20% / −5% / +10%，看着像严重回退；实际基线 prefill 出自 `cold_prompt.py` 的
  **10752 token 单形状 + /metrics 计数器增量**，decode 出自 `decode_probe.py` / `decode_conc.py`。
  按同形状同工具重测后三项立刻回到 ±1.3% 内。
  **「数值对不上」的第一嫌疑是口径，不是回退**；先回溯该数字的原始 JSON，再决定是否报警。

### 7.16 摘部件探针的兜底必须进真实输出；`asm volatile` 不等于「不会被删」

E-SELF-11 用 SASS + 计数器双向定位，推翻了 §7.13 里对 MODE 3 `ldsm=0` 的解释，并发现整个 sink 探针族失效。

- **nvcc 在 asm 的输出全部死掉时会连 `asm volatile` 一起删除**，与 GCC 的 `volatile` 语义不同。
  「我用了 volatile，所以这条指令一定在」是**错的**。
- 失效链条：兜底只写 `acc[0][0][0] = 1.f` → 无 MMA 时编译器把 acc 折成常量、落盘只需一个 select
  → sink 判死 → 全部操作数死 → ldmatrix 被删。**REG 133→56 就是这个折叠的指纹。**
- **硬规矩 (a)：摘部件探针的兜底必须写进真实输出**（真实累加器 / 全局内存），
  不能用「只喂一个条件常量」的 sink。
- **硬规矩 (b)：验收判据是指令计数器逐项相等**（`LDSM` / `shared_ld` / 总指令 / SASS 计数），
  不是「我认为操作数还活着」。本轮 MODE 8 的 LDSM=0、MODE 10 的 LDSM=41/64 都是这样抓出来的。
- **硬规矩 (c)：谓词化 vs 真分支会随数据流改变。** 同一个 `if (i < live)` 在 MODE 0 下被谓词化（4 个 i 全发射），
  在 MODE 10 下变成真分支（只发射 live 个，均值 2.5625/4 = 41/64）。**跨 MODE 比指令数前先核这一项。**
- **硬规矩 (d)：失真方向相反的两个臂可以夹逼出可信上界**，即使两臂都不保真。
  本轮「摘 tensor 管线 ≲2.5%」由 MODE 8（少 shared 读）与 MODE 10（多整数 ALU）反向夹逼得到。
- **硬规矩 (e)：「若 X 不爆则上 Y」是必要条件，不是充分条件。**
  凡这类判据必须**另算 Y 的收益上界**。本轮 MIO 仅 0.9%（不爆，通过），
  但 warp specialization 的发射解耦上界只有 **LDGSTS 占指令流 0.483%**，且发射占用仅 27.28%
  ⇒ 通过判据≠值得投。**先算上界，再看否决项。**
- **硬规矩 (f)：占用率类否决必须核「该配置能否真的达到那个 block 数」。**
  E-SELF-09 的「MINB=2 拿到 2 blocks 却更慢」是混淆结论：S=4/KB=4 的 shared 61440 容不下 2 block
  （需 122880 > optin 101376），那个占用率读数只能来自 S=3,MINB=2，与 S=3 自身 −1.3% 绑在一起。
  **写下「占用率翻倍却更慢」前，先用 shared × blocks ≤ optin 上限验算该臂是否自洽。**

**工程陷阱（本轮踩到）**

- **`grep | head` 在 `set -euo pipefail` 下会静默掐断整个循环**：head 提前关管道给 grep SIGPIPE，
  `set -e` 随即退出；若外层再套 `| tail`，退出码被掩盖成 0，看起来「成功但只跑了一臂」。
  改用 `sort -u` 等读尽输入的算子，或显式 `|| true`。
- **GB10 的 `smsp__average_warp_latency_issue_stalled_*.pct` 返回原始量级**（单位标 `%`，值却是周期级），
  必须按各 reason 合计归一。直接当百分比读会得到 4,303,133% 这种数。
- **`cuobjdump -res-usage` 用 `grep -A4` 会串到下一个函数的资源**，必须按 `Function` 块切分后逐块取。
- **`smsp__inst_executed_op_ldgsts.sum` 在 GB10 上可用**（13,328,640），
  补上了 §7.13「`ldgsts_cache_access` 报 0 不能推出无 cp.async」的直接证据缺口。

### 7.17 host 侧 API 时长不是 GPU 时间；表观带宽必须先判同期 GPU 忙闲

来源 E-FEED-01。本轮两次差点立错项，都是把 host 侧读数当成 GPU 读数。

**(a) 表观带宽 = 字节 / API 时长，只在「同期 GPU 空闲」时才是带宽。**
24 MiB 的 `cuMemcpyHtoDAsync_v2` 耗时 375–642 ms，算出 39–126 MB/s，看着像拷贝病了。
但同期 **GPU 忙 100%** ⇒ 这是 **pageable 源的 stream-ordered copy 成了隐式节流点**：
driver 分块 staging，host 被 GPU 消费速度反向限速。这段时间是**有效计算**，不是浪费。
**先算同期 kernel busy 占比，再决定这个时长该记在「浪费」还是「计算」账上。**
本轮若跳过这一步，会立一个 **53%** 的虚假上界（真实可回收只有 13.34%）。

**(b) 区间重叠 ≠ 严格包含。** 判「空隙内有没有 API」必须用 `x.start>=g0 and x.end<=g1`。
用重叠条件 `x.start<g1 and x.end>g0` 会把空隙**结束后**紧邻的 API 误算进内部，
据此能编出完全错误的故事（本轮首版即如此）。

**(c) 小形状 gate 的结论不可外推到大形状。**
`pageable-copy-gate-v2` 用 **4096 B** 测得 pageable 2.284 µs vs pinned 1.831 µs，判「差异可忽略」。
该结论只在 KB 量级成立：**24 MiB 下 pageable 的分块节流把 host 钉住 600 ms**，小包完全暴露不出这个效应。
**涉及 host↔device 传输的 gate，必须按生产真实字节数做，否则等于没做。**

**(d) 立「重采」计划前，先零成本验证采集假说本身。**
原计划改 `--cuda-graph-trace=node` 重采（停服 10–15 min），前提是「空隙 = graph 内 node 未记录」。
查原 trace 的 api 表发现全程 `cuGraphLaunch` 仅 **3** 次 ⇒ 假说直接否证，重采撤销。
**采集配置类假说往往能在既有数据里被证伪，不必先付重采的代价。**

**(e) 「GPU 三项都不饱和」时，要往 host 侧看，而不是继续拆内核。**
本轮根因是主线程在 `th.join()` 上等磁盘（engram 表 203 GB / 3.84 亿行，
49152 行 buffered gather 实测 671–696 ms）。此前近 20 项 GPU 内核干预收益有限，
因为卡点根本不在内核里。**沿因果链回溯时，链条可以跨出 GPU 边界。**

### 7.18 否证一条因果链，必须单独验证「干预是否真的生效」

来源 E-FEED-02。这是把「改造没用」升级为「因果假说被排除」的关键一步。

**(a) 端到端无收益有两种完全不同的原因，必须分开：**
① 干预本身没生效（实现无效 / env 没传到 / 形状不匹配）；
② 干预生效了，但**该机制不是瓶颈的原因**。
只测端到端会把两者混为一谈，从而错误地保留或丢弃一条假说。

本轮做法：端到端 A/B 判 pinned 无收益（三轮同向 −0.364%）后，**另做一个最小机制探针**
（`tools/pin-gate.cu`，24 MiB 真实尺寸 + GPU 带负载），实测 host API **81.879 ms → 0.002 ms**。
⇒ 干预有效约 4 万倍，于是**干净地否证了「upload 节流 → 预读起不来 → GPU 空隙」这条链**，
而不是留下「pinned 也许没实现对」的悬念。**机制探针的成本远低于它排除的歧义。**

**(b) 机制探针必须用生产真实形状与真实并发条件。**
历史 `pageable-copy-gate-v2` 用 4096 B **空载**测得 2.284 vs 1.831 µs，判「可忽略」；
生产是 24 MiB 且 stream 上排着几百 ms 的 kernel，pageable 的 host 被完全限速。
**空载小包与带载大包测的是两个不同现象。**

**(c) 身份断言的时间窗口必须锚到本次启动。**
`journalctl --since "-3min"` 会覆盖**上一臂**的日志，使 `PINNED=0` 臂误判为「已生效」。
取本次 restart 的时刻字符串传给 `--since`。A/B 脚本里这类窗口错误会直接伪造出结论。

**(d) 多条独立干预同向为负时，找它们共同副作用。**
本轮 AIO/O_DIRECT（绕过 page cache）、pinned（锁页挤占 cache）与历史 LEAD 全为负收益，
共同点是**都减少 engram 表的 page cache 可用量或命中**。
表 203 GB 而 `buff/cache` 仅 9 GB ⇒ 这类系统的 IO 侧优化要先把 cache 账算进去。
**推论：「把内存吃满」与「留住 page cache」可能是互相冲突的目标，须量化而非默认兼容。**

**(e) 改动基准必须是编出生产镜像的那棵树。**
Mac 的 `_upstream/tf` HEAD `ea64a870d` 与 Spark `build-alias` 的 `prompt.zig` sha256 不同，
且 Mac 版**没有** `TF_DS_ENGRAM_LEAD` 机制。按 Mac 行号改会改错位置、按 Mac 源码判断「上游没有某机制」会判错。
**跨机改动前先对比目标文件 sha256。**

### 7.19 引用历史 trace 前，必须核对采集时刻到当前之间的**全部已落地配置变更**

来源 E-FEED-01 / E-FEED-02 的重大失误（2026-11-25）。**这是本项目目前代价最大的一次方法论违规。**

**发生了什么**：用 `forge-20261123-steady-trace`（11-23 采集）归因 11-25 的 prefill 问题，
得出「663.5 ms 空隙 = 13.34%，卡点在 host 侧 engram 磁盘读」，并据此做了 pinned 改造与三轮 A/B。
**但 11-24 的 E-ENGRAM-01 已落地 `ENGRAM_AIO=0`（+19.5%），那批空隙当时就被消除了。**
`01-发现与结论.md` §6.5 早已用零注入 PM 采样判决：当前 **>10 ms 空闲段 0 个、最长 0.2 ms、空闲 0.04%、GPU 繁忙度 99.96%**。
⇒ 两轮工作优化的是一段**已经不存在的时间**；pinned 无收益的真因不是任何新机制，而是**靶子没了**。

**硬规矩**

- **(a) 拿任何历史 trace/读数立项前，先列「采集时刻 → 现在」之间所有已落地的配置变更**，
  逐条判断是否影响该读数的口径。查 `docs/performance/00-当前进展.md` 的落地记录与 `03-实验与证据索引.md`。
  **这是 §7.2 的延伸：§7.2 管「这个问题是否已被解决」，本条管「这份数据是否还代表当前」。**
- **(b) 形态吻合要当作警报，不是当作确认。** 本轮四个空隙 132–216 ms 与 §6.5 旧 AIO=1 的「7 段 166–219 ms」
  高度吻合——那正是「我看的是一份旧配置数据」的指纹，我却把它当成了归因成立的证据。
- **(c) 已兑现的收益不可再计一次。** 「空隙归零 ⇒ +15.4%」在 11-24 已经兑现为 1773→2118。
  对同一块时间第二次立项，Amdahl 上界是**虚的**。
- **(d) 端到端否证后，先回头质疑靶子是否存在，再编新机制假说。**
  本轮 pinned 无效后我又提出「磁盘读绝对时长超过重叠窗口」，而正确动作是去查 §6.5——
  那里连「读没有消失，只是从阻塞 GPU 变成与 GPU 重叠」都写明了。
  **新假说的成本远高于查一次既有判决。**
- **(e) 不要用统一解释去归纳机制不同的多个负结果。** 本轮把 AIO 与 pinned 的负收益都归给 page cache，
  而 AIO 的真因 §6.4 早已查明是**单线程 O_DIRECT 挤爆单硬件队列 1023 tags**（抖动 15.6%→0.9% 是其指纹）。
  **归纳前先逐个查既有归因。**

**当前的正确定位（供后续立项直接用）**：GPU 时间已吃满（繁忙度 99.96%，空闲已榨干），
**没有「等待」可再回收**；限制是 **GPU 忙但效率低**（DRAM 49.3%、Tensor 37%、发射 36.2%）。
下一步只能**减少真实 GPU 工作量或提高内核效率**，与 E-SELF-08/09/10/11 的结论一致。
