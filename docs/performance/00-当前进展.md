## 3. 当前基线与4000缺口

- 本轮自然技术文档冷前缀：约8K **1700–1739 tok/s**、约16K **1750–1780 tok/s**（不同实验请求，不是新统一中位数）。[原A/B数据](<../../runs/forge-20261123-interleave/prefill-summary.json>)。
- **2026-11-24 落地 `ENGRAM_AIO=0` 后的新基线**：约8K（10 752–10 755 tok）**稳态 2102.80–2122.69，中位 2118.65**（n=6，剔除重启后首请求）；约41K（41 364–41 368 tok）**2201.63–2204.06**。原配置同负载中位 1773.36 / 1833.80。[新A/B原始数据](<../../runs/forge-20261124-engram-aio/REPORT.md>)。
- 用可复算的稳态head请求为预算锚点：N=8628，kernel窗口4.972653679s；对应约1735.09 tok/s。server prefill约4.977s，两口径不能混为精确同一值。[账面原始数据](<../../runs/forge-20261123-bottleneck-ledger/ledger.json>)。
- 新目标的**条件预算**：8628/4000=**2.157s**；相对该kernel窗口需减少**2.815653679s（56.62%）**。这不是4000正式验收，也不是严格物理不可达判决。
- 最大单项：专家核心约1.909s；其他GPU与通信工作、head空隙仍显著。具体拆分见[时间账](<01-发现与结论.md#2-时间账与4000条件>)。

## 5. 下一步，按判决价值而非调用栈长度排序

0. **已完成（本轮）**：硬件 roofline 分母实测。GB10 DRAM 读 **246.2 GB/s**、FP16 GEMM **100.82 TFLOPS**、
   平衡 **409.4 FLOP/byte**；专家核心 AI **204.4** ⇒ **带宽侧**，距带宽屋顶 **2.00×**。
   **算力不是绑定约束**；双 Spark 聚合带宽 492.4 GB/s 低于 Mac Studio 实测 707.9 GB/s。
   见 [E-ROOF-01](<../../runs/forge-20261123-roofline/REPORT.md>)。

0b. **已完成（E-DRAM-01 r2）**：2.00× 缺口**已分离**。零注入设备级 PM 采样实测
   chunk DRAM 均值 **121.5 GB/s = 屋顶 49.3%**，>200 GB/s 仅占时 **9.8%**，
   **不存在 H1 要求的约 400 ms 满带宽平台 ⇒ DRAM 重读解释被否证，内核效率缺口成立**。
   重读被 L2 吸收（L2 请求 742.2 GB/s、命中率 84.5%）。
   机制候选：**低占用延迟受限**，实测 Occupancy 中位 **17%**，DRAM/Issue/Tensor 三条饱和度同时都低。
   见 [E-DRAM-01](<../../runs/forge-20261123-dram/REPORT.md>)。
   **r1 是内存事故（人工拔电源），硬约束见 [§0](<01-发现与结论.md>)。**

0c. **已完成并落地（E-ENGRAM-01，2026-11-24）**：**首个兑现端到端收益的单变量改动。**
   `ENGRAM_AIO=1`→`0`。机制：单线程 O_DIRECT 每批提交 2048 个读，经 blk-mq 落同一硬件队列
   （1023 tags），`io_submit` 阻塞等 tag 回收 ⇒ `start_ms` 225–237 ms 而 `wait_ms` 仅 5–12 ms；
   读放大 **31.03×**（有用 6.19 MiB / 请求 192 MiB）。改走 reader pool 多线程+页缓存后：
   **8K 1773.36→2118.93（+19.5%）、41K 1833.80→2202.84（+20.1%）**，
   **B 最小值 1955.22 > A 最大值 1789.16（分布不重叠）**，抖动 15.6%→0.9%，
   内存最低点反而更高。另测 `AIO=1+LEAD=1`（C）不如 B。
   **零构建、零额外内存、一键回滚。** 见 [E-ENGRAM-01](<../../runs/forge-20261124-engram-aio/REPORT.md>)。

0d. **卡点已彻底疏解，非部分改善（2026-11-24 直接判决）**：不依赖分段阈值，直接数
   `GR Engine Active ≤20%` 采样——旧 **17.55%**（1.1187 s，7 段 >10 ms、最长 218.82 ms）
   → 新 **0.04%**（0.0020 s，**0 段 >10 ms**，仅 10 个孤立单点）。**GPU 繁忙度 99.96%。**
   交叉验证：prefill 省的 1.2076 s 中 **1.1167 s（92.5%）是空隙**，真实 GPU 工作仅 −0.8%
   ⇒ **省的是等待不是工作**，Engram 的读改为与 GPU 重叠而非消失。
   **⇒ 空闲已榨干；下一步只能减真实工作量或提内核效率。**

1. **❌ 专家内核方向已关闭（2026-11-24 Review 判决）**：占用率绑定项是 down 内核
   `grouped_rows_kernel<2,8,4,1,2,10,2,false>` **REG 255**（CUDA 上限）⇒ 16.7%。
   **全部 cubin 变体算下来占用率不变**，且 kit 无 `.cu` 源不能降寄存器重编译。
   **那 2.00× 缺口本地拿不到，不要再投入。** 见 [结论 §6.6](<01-发现与结论.md>)。
2. **❌ collective 方向已关闭（E-COLL-01 实测判决，2026-11-24）**：
   实测线上字节 **11.28 GB/请求**（约 1 MiB/token，KV shard 流量为 0），
   双 rail 可达带宽 **23.15 GB/s**（`ib_write_bw` 实测，非线速换算）
   ⇒ 纯搬运最短 **487 ms**，collective 内核 647–672 ms
   ⇒ **非传输部分仅 159–184 ms（窗口 3.1–3.6%）**，若 NCCL 效率 80% 则趋近零。
   **Review 估的 405–472 ms 自旋被推翻**（字节低估 2.7× + 带宽高估 2.16× 同向叠加）。
   **根因：CX7 多宿主，双 twin 共享 2×Gen5 x4；本机已绑双 twin，实测 185.19 Gb/s = 200G 物理口线速的 92.6%（原「单 x4 卡死」归因已更正）。**
   **MTU 1024→4096 实测无收益（−0.20%），已回滚。**
   见 [E-COLL-01](<../../runs/forge-20261124-collective/REPORT.md>)。
3. **关键路径校准**：同一请求的GPU需求时刻、host层ready、两rank消息就绪与时钟误差对齐。
4. **加大 chunk —— 已被双重否决，不再作为首选杠杆**：
   ①**Amdahl 否决**：专家 core 归零上限仅 **2815.83 tok/s**，专家 core+全部间隙都归零仍剩
   2.393413 s ≈ 3605 tok/s，**均低于 4000 目标**（[时间账](<01-发现与结论.md#2-时间账与4000条件>)）。
   ②**内存否决**：chunk 4096 的 arena 增量 **1.31–3.68 GiB**，而生产多路 KV 下 head 最小空闲
   仅 **4.8 GiB**、memguard 地板 2.5 GiB ⇒ 可用余量 2.3 GiB 装不下；8192 档最坏情形直接为负。
   另 `POOL=1052672` 对 4096/8192 均不整除会 `BadPoolSize` 拒绝启动，B 本就不是单变量。
   测算见 [E-CHUNK-MEM](<../../runs/forge-20261124-chunk-mem/REPORT.md>)。**如要重启此项，须先降 CONTEXT 腾内存并接受产品能力变更。**
   **⚠ 更正（E-KVOFF-01）：降 CONTEXT 这条路也已被堵死**——KV 池实测仅 **0.52 GiB**，
   随 CONTEXT 变的总量只有 0.770 GiB（KV+RoPE），减半仅释放 **0.386 GiB**（原估 2.5 GiB 高估 6.81×）。
   卸全部 KV 也只到 2.82 GiB < 需求 3.40 GiB。**不改引擎则 chunk 4096 方向关闭。**

4b. **❌ 权重卸载 SSD 换 chunk 8192 已否决（E-OFFLOAD-01，2026-11-24）**：
   prefill 专家 **100% 热**（每 chunk 重读缓存 97.2%），无"不频繁"子集；
   真正冷权重仅 **1.464 GiB/rank**（embed 1.233 replicated + head 0.231），
   而 8192 结构缺口 **5.40 GiB**，覆盖 27%。卸热专家在完美重叠下仍**净亏 26.6%**
   （SSD 5.69 GB/s vs 专家核 123.34 GB/s，差 21.7×；平衡点 4.27 GiB）。
   引擎 `cuda.DeviceBuffer.alloc` 全量驻留，**无分页路径**。
   观察项：embed BF16 未切分，切分可省 0.617 GiB/rank（引擎改动，暂不动）。

4c. **Decode 已独立测清（E-DECODE-01，2026-11-24）**：口径谜团解开——
   N=4 聚合 **110.0** / 每路 **27.5**，N=2 聚合 83.1 / 每路 41.5，N=1 61.4。
   **DRAM 均值 203.9 GB/s = 屋顶 82.8%（中位 89.7%），GR 活跃 95%，Tensor 仅 13.1%**
   ⇒ **decode 与 prefill（49.3%）性质相反，已近带宽极限，剩余约 +20%（→132.8 tok/s）**。

4d. **❌ KV 卸载 SSD 换 chunk 4096 已否决（E-KVOFF-01，2026-11-24）**：
   源码精确公式算得 KV 池 **532.07 MiB**、replicated 893.48 MiB，与引擎日志 **双值吻合**
   ⇒ **KV 从来不是内存大头**（只 4 层是 KV 源 + 稀疏注意力）。
   卸全部 KV 后可用 2.82 GiB，仍缺 0.58 GiB。**连带作废 §6.9 与 review §5.4 的 +23.0% 投影。**
   spill v2 已在做「空闲会话 KV 落盘」，活跃池无分页路径。

4e. **✅ kit v0.7.5 超集 + 16流/32行 已上生产（E-KIT-01，2026-11-24）**：
   **16 流聚合 110.0 → 197.16 tok/s（+79.2%）**，单流不变，arena 3766→4000 MiB（+234 MiB）。
   kit 是严格超集（198/198 内核逐字节保留），**免重编译**，引擎 pin 与 52 patch 全不动。
   **机制**：ROUND_ROWS 是上限不是目标——4 流填不满 16 故无效；
   **16 流 + R=16 时 MTP 被静默关闭**（depth = 16/16−1 = 0），R=32 才恢复。R=48 反而更慢。
   **单人单流零收益**，收益只在多路并发兑现。生产多路负载下未复验。
   **⚠ 追加判决：用户实际只跑 ≤4 路，故该收益对其场景不适用。已退回 PARALLEL=4 / ROUND_ROWS=16，
   arena 回到 3766 MiB（与基线同值），仅保留新 kit（严格超集、arena 零增量、后续 v0.7.5 工作的底座）。**
   补测：16流槽/R32 下跑 N=4 = 108.38；退回后 N=1 59.75 / N=4 109.23，均在基线噪声内。
   另查 `TF_DS_IDX_SPLIT`（8192 索引切分）**我方 pin 不支持**，需换引擎。
   **要在 ≤4 路拿到提速，只能走引擎重端口（50 patch）。**
