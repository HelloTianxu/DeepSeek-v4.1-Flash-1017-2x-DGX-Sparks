# 发现与结论（性能研究现行口径）

校准日期：2026-11-23，Asia/Shanghai。范围限定为本项目的双Spark实验，不替代原仓库历史成绩或Mac实验。证据等级：【工程实测】真实计时/配置/工件核对；【理论推导】数据+明确前提；【研究假设】未完成因果验证。每项关联原始证据，所有历史日志中的冲突以本页现行限定为准。

## 0. 内存安全硬约束（做任何实验前先读，违反会要求人工拔电源）

【已发生的事故】2026-11-24 00:0x，E-DRAM-01 第一次尝试在**模型驻留**状态下用
`ncu` 多 pass kernel replay profile 真实专家内核，**把 head 节点内存打爆**：
ICMP 可通但 sshd banner exchange 超时（两条链路均如此），worker 正常，
**只能由用户人工拔电源恢复**。两台机器无头、无远程开关，爆内存的恢复成本是人工到场。

**第一性原理根因**：GB10 是**统一内存**（LPDDR5X），GPU"显存"就是主机 RAM。
每节点 **128 GB**，TP2 两 rank 各驻留约 104 GB 权重+KV，**实际富余仅 5–8 GB**。
`ncu` 的 kernel replay 为保证多 pass 语义一致，必须**保存并恢复内核可能写的设备内存**；
在统一内存机上这就是主机 RAM，面对约 104 GB 的进程分配，其 save/restore 缓冲远超 5–8 GB 富余
⇒ 必然 OOM。**这不是参数没调好，是方法与该硬件的内存结构不相容。**
（这也解释了既有 §7 "不能 production multipass profiling/重放" 的判断是对的。）

**硬约束（此后一律遵守）**：

1. **禁止**在模型驻留时使用任何 kernel replay 类 profiling（`ncu` 默认 `--replay-mode kernel`、
   多 pass metric set、`--cache-control all` 的重放）。驻留态只允许**无重放**的观测：
   system-wide GPU PM 采样（`nsys --gpu-metrics-devices`，不注入引擎进程）、引擎自带 `--profile`、
   `/metrics`、只读 trace。
2. **任何实验容器必须带硬内存上限**：`--memory=<N>g --memory-swap=<N>g`，
   让 OOM killer 杀容器而不是冻住整机。host 侧工具用
   `systemd-run --scope -p MemoryMax=<N>G -p MemorySwapMax=0`。
   **没有上限的实验容器不许启动。**
3. **需要重放/大工作集时，必须先停服**，让富余回到约 113 GB，并把工作集显式限制在个位数 GB；
   停服前落盘 `RESTORE.md`。
4. **不得绕过 `start.sh` 的 memguard**：本轮事故中我手动 `docker run` 复制命令，
   `memguard_start` 未运行，失去了低内存自动杀 rank 的保护。
   若必须手动起容器，须同时自行启动等效 memguard，或改用不注入引擎的观测路径。
5. 每次实验前先读 `free -g` 的 available，**富余 < 10 GB 时不做任何新增分配**。
6. **【2026-11-24 用户给出的生产基线，优先于空载读数】** 生产多路上下文、KV Cache 累积时，
   **head 节点空闲约 5 GB 上下抖动，最小 4.8 GB**。空载单流读到的 8.2–8.7 GB **不代表生产**。
   任何"装得下"的判定必须用 **4.8 GB** 作基线，减去 memguard 地板 2.5 GB，
   **可用余量只有约 2.3 GB**。引擎自报 `121.63 − 104.54(model) − 12.2(reserve) = 4.86 GiB` 与之吻合。
7. **不得下调 `TENSORFOLD_MEMORY_RESERVE_GIB` 来腾地方**（config.sh 原注：
   引擎会把 reserve 也吃掉，曾有 rank 0 带 10 GiB reserve 冻死 Spark）。

## 4. 专家形状、指令与资源

【实测工件】实际专家SASS为HMMA.16816.F32（FP16输入/FP32累加），不是NVFP4路径。gate/up106regs、256threads、44288shared bytes；down255regs、128threads、32896shared bytes。[指令报告](<../../runs/forge-20261123-moe-sw/INSTRUCTION-ANALYSIS.md>)。

【理论上界】实际GPU属性48SM、1536threads/SM、65536regs/SM、102400shared/SM，gate/up驻留最多16/48warps，down8/48。[属性](<../../runs/forge-20261123-bottleneck-ledger/cuda-device-attributes.json>)。驻留上界不等于测得occupancy，也不能推3倍/6倍收益。

【工程实测】同请求成对gateup/down后中位：R2048约20.162ms、R436约9.733ms、R128约4.973ms。[逐层配对数据](<../../runs/forge-20261123-bottleneck-ledger/layer-shape-ledger.json>)。总pairs=R×7不是单专家GEMM的M；layer/序列位置/routing/cache不同。按bulk加权单位pair成本外推小形状可减约190.9ms只是条件投影，不是实测/上界。[形状审计](<../../runs/forge-20261123-shape-audit/REPORT.md>)。

实际DRAM字节、执行FLOP、动态解码指令和同格式可持续吞吐均缺失。roofline应同时检验Fexecuted/C、Bdram/BW、Idecode/R；不能用273GB/s或FP4理论值倒推出唯一原因。

## 6. Engram供给：已实证的局部机制

### 6.1 GPU位置与host时间不可混同

旧同请求GPU trace四大空隙216.106/161.824/152.981/132.638ms，总663.549ms，位于完整chunk第1层Engram入口。[相邻kernel](<../../runs/forge-20261123-bottleneck-ledger/gap-neighbors.json>)。未与新host时标在同一请求对齐，不能直接算可回收量。

【静态+动态核对】生产binary存在串行双层read、wholejoin、成对4KiB对齐请求。[binary证据](<../../runs/forge-20261123-bottleneck-ledger/LIVE-MECHANISM.md>)。后续chunk动态每层约225–243ms、主线程wholejoin约454–483ms；进入join时j0尚未完成，j0成功返回后还等j1约225–241ms。[原事件](<../../runs/forge-20261123-bottleneck-ledger/engram-host-trace-v4.txt>)、[摘要](<../../runs/forge-20261123-bottleneck-ledger/host-event-summary.json>)。函数成功返回不是指令级ready采样；主机join可被前chunkGPU覆盖。

### 6.3 实际请求量与队列匹配

【工程实测】完整层每rank实际24次io_submit、49152个请求全部接受、错误0；accepted不等于completed。原始计数见上表submit摘要。

Engram weight256bytes、scale8bytes，TP2每rank12行/token；每2048token有效24576行、有效6.488064MB。实际offset+机器码计算每行至少2×4KiB请求，最低201.326592MB=31.03×；均匀row_id mod16时weight1/16跨界，平均207.618048MB=32×。[offset与几何](<../../runs/forge-20261123-bottleneck-ledger/engram-block-geometry.json>)。**不是实测disk traffic**，去重/缓存/完成字节未测；仅修对齐条件字节降3.03%，不消灭全部放大。

【配置实测】Engram位于本地NVMe ext4，YMTC PC450-2TB-D；16hwqueues，每queue1023tags，nr_requests1023，driverdepth1024，scheduler none。[原配置](<../../runs/forge-20261123-bottleneck-ledger/nvme-queue-config.json>)。默认128浅队列解释不成立。

【理论推导】batch2048reads约2.002×单queue1023tags，ring4096reads约4.004×；与tagwait机制匹配，但实际CPU/queue分布与完成复用尚未测。[队列账](<../../runs/forge-20261123-bottleneck-ledger/nvme-queue-account.json>)。聚合16队列不等于单reader可用capacity，burst>depth也不意味每次必睡。

### 6.4 因果对照已完成并落地：`ENGRAM_AIO=0`（E-ENGRAM-01，2026-11-24）

§6.1–6.3 的机制链（tag 等待、31× 放大、单队列 2.002×）**此前只有观测，没有改机制后的对照**。
本轮补上，**是本项目首个兑现端到端收益的单变量改动**。

| 配置 | 10 753 tok 中位 | 区间 | 41 367 tok 中位 |
|---|---:|---|---:|
| A `ENGRAM_AIO=1`（原配置） | 1773.36 | [1547.19, 1789.16] | 1833.80 |
| C `AIO=1 + TF_DS_ENGRAM_LEAD=1` | 1903.46 | [1729.33, 2002.24] | 2137.23 |
| **B `ENGRAM_AIO=0`（采纳）** | **2118.93** | [1955.22, 2122.69] | **2202.84** |

**【工程实测】B vs A：+19.5%（8K）、+20.1%（41K）。**
B 稳态 n=6 中位 **2118.65**，跨度 **0.9%**（A 为 15.6%）。
**判据用分布不重叠**：B 最小值 1955.22 > A 最大值 1789.16，不靠均值差。

**机制**：`AIO=1` 走单线程 O_DIRECT，每批 2048 读经 blk-mq 落同一硬件队列（1023 tags），
`io_submit` 阻塞等 tag 回收；`AIO=0` 走 reader pool，多线程打散队列 + 页缓存对重复 4 KiB 块去重。
**不改任何数值内核、模型、量化，不改数学执行。**

**混淆已处置**：①A 走 O_DIRECT 不填页缓存；②B 的 41K 长 prompt 约 3/4 内容为冷仍立刻达 2201.63
⇒ 主机制不是缓存焐热；③重启后首请求偏低（1955.22 / 1943.02）每次重启复现，判为预热，稳态统计中剔除。

**内存**：B 期间最低 8.266–8.314 GiB，**始终高于 A 的 8.199**，未见页缓存挤压 MemAvailable。
**边界**：均为空载单流；**生产多路（§0 第 6 条 4.8 GiB 基线）下未实测**，上线后须观察。

**回滚**：`cp scripts/local.sh.engram-ab-bak scripts/local.sh` + systemd restart，无构建。

### 6.5 卡点已彻底疏解（不是部分改善）——直接判决

端到端变快不等于卡点消失。用**零注入 GPU PM 采样**、**不依赖分段阈值**的口径
（直接数活跃窗口内 `GR Engine Active ≤ 20%` 的采样点）同法对照：

| | 活跃窗口 | GR≤20% 采样 | **空闲占比** | **>10 ms 空闲段** | 最长段 |
|---|---:|---:|---:|---:|---:|
| 旧 `AIO=1` | 6.3754 s | 5593 / 31877 | **17.55%**（1.1187 s） | **7 个，合计 1.0975 s** | 218.82 ms |
| **新 `AIO=0`** | 5.1678 s | **10 / 25839** | **0.04%**（0.0020 s） | **0 个** | **0.2 ms** |

**【工程实测】Engram 卡点已彻底疏解，prefill 期间 GPU 繁忙度 99.96%。**
旧的 7 段长空闲（166–219 ms）全部消失；新的 10 个空闲采样均为孤立单点（各 0.2 ms），非卡点。

**交叉验证——省的是等待不是工作**：prefill −1.2076 s 中 **1.1167 s（92.5%）来自空隙消除**，
而 busy_regions 合计（真实 GPU 工作）5.2098→5.1666 s，**仅 −0.8%**。
Engram 的读没有消失，是**从阻塞 GPU 变成与 GPU 工作重叠**。
分段结构印证：5 个独立 chunk 区段因空隙消失而合并，区段数 9→4。

**战略含义**：**空闲已榨干，没有「等待」可再回收。** 下一步只能减少真实 GPU 工作量或提高内核效率。
**collective 0.539 s 的可回收性需重新评估**——本轮已看不到 >10 ms 的 GPU 空闲，
说明它主要是与 GPU 工作重叠的传输/peer 等待，不是纯空转。

**边界**：PM 采样下测得（采样开销约 1.8%），单请求单流空载；
`GR≤20%` 是「非繁忙」不是「零指令」，故 0.04% 是空闲**上界**，结论方向保守；worker 侧未测。
[判决全文](<../../runs/forge-20261124-engram-aio/REPORT.md>)、`idle_direct.py`。

r1 因 FLOP 按三矩阵计却只分配两矩阵而作废，保留 `roofline-r1.json`）：

| 项 | 实测 | 官方 | 达成 |
|---|---:|---:|---:|
| DRAM 可持续读（67.11MB 工作集） | **246.2 GB/s** | 273 | **90.2%** |
| DRAM 可持续读（8589.93MB） | 241.0 GB/s | 273 | 88.3% |
| FP16 稠密 GEMM 16384³ | **100.82 TFLOPS** | — | — |

**机器平衡 409.4 FLOP/byte。** 设备 SM 12.1、48 SM、**L2 仅 24 MB**。
L2 驻留参照 25.03MB→502.1、8.26MB→715.0 GB/s，**这不是 DRAM**。

【工程实测】真实专家形状（E384、D5120、本地 I1152、FP16 权重恒 13.59GB）：
**M 从 2 到 64（32 倍）耗时只 58.120→60.796 ms（+4.6%）**；
M=32 权重带宽 **224.9 GB/s = 实测 DRAM 峰值 91.3%**。
真实路由 M̄=R×6/384：R2048→32、R436→6.8、R128→2，**全部带宽侧**。
（bmm 为 cuBLAS FP16 稠密路径，非 EXL3 融合解码内核，绝对耗时不可当生产可达值。）

【理论推导，分母已实测】生产 R2048：有效 FLOP 507.3 GFLOP、唯一字节 2.482 GB、core 20.162 ms
⇒ **算术强度 204.4 FLOP/byte < 机器平衡 409.4**，**唯一字节带宽 123.1 GB/s = 峰值 50.0%**，
**带宽屋顶最短 10.08 ms，实测/屋顶 = 2.00×**。

**因此 §1「尚未证明算力已到顶」现在可以收紧为：专家核心不是算力受限，是带宽侧。**
§4 缺的"同格式可持续吞吐"已补。

**2.00× 缺口的两种解释已于 §9.3 分离（E-DRAM-01 r2）：①tile 重读打到 DRAM 已被否证，②内核效率缺口成立。**
下面两行保留为 E-ROOF-01 当时的原判，现行结论以 §9.3 为准：
①实际流量≈2×唯一字节（tile 重读）⇒ 已在屋顶，可回收的是消除重读；
②融合解码内核效率低 ⇒ 123.1 GB/s 是真实流量，尚有一倍空间。

### 9.2 加大 chunk：条件投影，**已被 Amdahl 与内存双重否决（2026-11-24）**

> **状态更新：本节不再是首选杠杆。** 两条独立否决见文末，测算见
> [E-CHUNK-MEM](<../../runs/forge-20261124-chunk-mem/REPORT.md>)。以下投影保留作历史与机制记录。

专家耗时对 M 不敏感 ⇒ 每 token 专家成本 ≈ 权重读 ÷ M。
M=32→128（chunk 2048→8192）耗时 +9.2% 而 token ×4 ⇒ **每 token 专家成本 ÷3.66**。
条件投影：专家 core 1908.5→≈734.8 ms，窗口 4972.65→≈3798.9 ms，**≈2271 tok/s**。
**这是其他分类不变的反事实，不是实测收益、不是上界**；chunk 变大同时改 collective 次数、
attention/HC 形状与激活/KV 峰值内存，必须单变量 A/B。

【工程实测】**阻塞点**：`chunk_rows = 2048` 是编译期常量
（`zig/patches/0008-pool-window.patch`），出厂 `tensorfold-native` 的 strings
**无 `TF_DS_PREFILL_CHUNK`**（patch 注释提到但二进制不支持，**上游源码里同样只是注释**）
⇒ **调 chunk 须改 patch 重编译**。本轮未构建。

**【否决一：Amdahl】** 本投影的 ≈2271 tok/s 与 §2 时间账一致地指向同一事实：
**专家 core 归零上限仅 2815.83 tok/s**，专家 core + 全部间隙都归零仍剩 2.393413 s ≈ 3605 tok/s。
**chunk 杠杆的数学天花板低于 4000 目标**，不能作为达标主线。

**【否决二：内存】** 逐项测算 `prompt.Chunk.init` 的 cap 线性分配（cap == chunk_rows，
最大单项专家 scratch 594.5 MiB @2048）：

| 档位 | arena 增量 | 以生产 4.8 GiB 基线、地板 2.5 GiB 计 |
|---|---|---|
| 4096 | +1.31 .. +3.68 GiB | 余量仅 2.3 GiB ⇒ **结构估计与最坏情形均跌破地板** |
| 8192 | +3.94 .. +11.03 GiB | **最坏情形直接为负** |

另 **`POOL=1052672` 对 4096/8192 均不整除**（`cap % (parts*chunk_rows) != 0 → BadPoolSize`），
必须同改 POOL；`model.zig` 与 `parts.zig` 两处常量有断言须同改；chunk_rows 进 spill tier identity。
**B 本就不是单变量。** 且 parts=2 时 POOL ≥ 2×WINDOW，当前已贴下界，
**不降 CONTEXT 就腾不出内存**。

**【已排除的替代】** `TF_DS_PROMPT_WINDOW_ROWS`（默认 64，上限 128）与
`TF_DS_PROMPT_GEMM_ROWS`（默认 128，上限 128）对 2048 行主体都不触发，无法替代；
且两路径舍入不同，属**有损**开关。

### 9.3 2.00× 缺口已分离：内核效率缺口，不是 DRAM 重读

【工程实测】E-DRAM-01 **r2**（[报告](<../../runs/forge-20261123-dram/REPORT.md>)）。
**r1 是内存事故、无数据**（见 §0）。r2 引擎照常运行、**零注入、无内核重放**，
用设备级 GPU PM 采样（`nsys --gpu-metrics-devices`，metric set GB20y-top，5 kHz），
采样容器带 `--memory=2g` 硬上限，全程 available 稳定 8 GB。

**两个必须记住的口径陷阱**：
1. GB10 **无 `dram__*` 计数器**；`aperture_device` 口径实测恒为 **0**（统一内存归 sysmem）。
2. 标着 `[GB/s]` 的 VidL2 字段，sqlite 原始值是 **sectors/s**，须 `×32/1e9`。
   用已知字节 streaming 校准两次：10 kHz 误差 **0.184%**、5 kHz **0.241%**，与频率无关。

【工程实测】冷前缀 10755 token、cached 0、prefill 6.376158 s ⇒ **1686.75 tok/s**（零注入真实速度）。
繁忙期自然分成 5 个 877–942 ms 区段 + 321.8 ms 尾段，对应 5×2048+515。最大 chunk 941.6 ms：

| 量 | 实测 |
|---|---:|
| DRAM 均值 | **121.5 GB/s = 屋顶 246.2 的 49.3%** |
| 中位 / p90 / 最大 | 124.0 / 207.8 / 265.3 GB/s |
| 时间占比 > 200 GB/s | **约 9.8%** |
| 最长高带宽连续段 | **3.6 ms** |

**判决**：H1 要求每 chunk 有 403.2 ms（42.8%）贴近 246 GB/s 的平台，
**实测不存在该形态** ⇒ **H1（tile 重读打到 DRAM、已在屋顶）被否证**；
**H2 成立：123.1 GB/s 基本就是真实 DRAM 带宽，2.00× 是内核效率缺口。**
该判决基于整 chunk 形态，**不依赖任何相位门控**。

【工程实测】重读确实存在但**被 L2 吸收**：Tensor>20% 相位（360.8 ms，占 chunk 38.3%）
DRAM 115.5 GB/s、**L2 请求 742.2 GB/s（6.43×）、读命中率 84.5%**。
**重读 ≠ DRAM 重读**，这是 H1 推理链断掉的地方。

【工程实测】机制候选：**低占用延迟受限**。该相位三条饱和度同时都低——
DRAM 46.9%、SM Issue 36.2%（Tensor>60% 时仅 13.0%）、Tensor Pipe 37.0%；
而**实测 Occupancy 中位数仅 17%**，与静态驻留上界吻合（down 8/48=16.7%、gateup 16/48=33%）。
**首次用实测占用率证实静态推算。** 具体 stall 原因（long scoreboard / barrier / 解码依赖链）
需 stall-reason 计数器，PM 采样给不了，**未分离，不宣称已识别 stall 根因**。

【工程实测，未追】chunk 内 GPC 频率均值约 **2238.6 MHz**，上限 3003 MHz，
**prefill 未跑在最高时钟**；GB10 CPU/GPU 共享功耗预算，可能是独立杠杆。未做降频归因。

**对 §9.2 的影响**：加大 chunk 多了机制性理由——内核是低占用延迟受限而非带宽饱和，
增大 M 提高算术强度与内存管线重叠，**收益不以"打满带宽"为前提**。
新候选次级瓶颈：L2 请求已达 742–1170 GB/s，**L2 屋顶未测，不做预测**。
