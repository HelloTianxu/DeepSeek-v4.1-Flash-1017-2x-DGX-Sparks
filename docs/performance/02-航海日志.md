## 2026-11-23 · interleave与FIX_K单变量筛查

**假设A**：`PREFILL_INTERLEAVE_MS=250`可能无条件拖慢prefill。

**结果**：改0未获得稳定单流收益；代码审查表明只有其他runnable decode时才插入调度，不能把250ms乘chunk数。保留0是配置选择，不计加速。

**假设B**：固定5候选可提高decode有效输出τ。

**结果**：候选增加、轮次略降，但每轮成本上升更多。代码83.14→75.64，长文61.00→48.36 tok/s，撤回FIX_K5。有限样本输出一致不是普遍质量证明。

**路线修正**：不能把“变量生效”当“目标改善”；所有decode方案同时报τ和T。

## 2026-11-23 · Engram供给逐层收敛

**阶段分解**：8个完整层准备中AIO占99.17%；hash0.5–0.7ms、decode1.3–1.9ms，停止优先优化hash/decode。

M=32 权重带宽 224.9 GB/s = 峰值 91.3%。**普通 FP16 grouped GEMM 在这个形状已贴带宽屋顶。**

## 2026-11-24 · E-DRAM-01 r1：内存事故，方法被硬件否证

用户授权原话："先A后B吧，这个环境你是可以停机操作研究的 我可以暂时用云上模型"。
目标：分离专家核心 2.00× 带宽缺口（tile 重读 vs 融合解码内核低效）。

**本轮拿到的可复用正向事实（与事故无关，均经校准）**：

1. **profiling 权限门已打通且不改 host**：`RmProfilingAdminOnly: 1`，
   但用户在 docker 组，`docker run --cap-add SYS_ADMIN` 即可让 ncu 成功 connect 并 profile。
   host 驱动参数保持 1 未改。
2. **GB10 没有 `dram__*` 计数器**（5338 个 metric 中 `dram` 仅出现在描述文字里）。
   `lts__t_sectors_aperture_device_lookup_miss.sum` 实测返回 **0**——
   因为统一内存机的 LPDDR 访问被归类为 **sysmem 而非 device vidmem**。
   **用错 aperture 会把"零流量"当成事实。**
3. **已校准的 GB10 DRAM 读口径**：`lts__t_sectors_op_read_lookup_miss.sum × 32B`。
   用已知 1.0737 GB 的 streaming reduce 校准：实测 1.0739 GB，**误差 0.01%**；
   `lts__d_sectors_fill_sysmem.sum × 32B` 给 1.0748 GB（0.09%），可作交叉核对。
   `op_read`（L2 请求）与 `op_read_lookup_miss`（DRAM）之比即"重读是否被 L2 吸收"。
4. **真实专家内核身份**：`tf_exl3x::grouped_mma_kernel<2,2,10,true,4>`，
   在 `kit/cubins/experts_cb.cubin`（49.5 MB），**手写 CUDA 而非 Triton AOT**；
   demangle 后 19 个参数（2×`__half const*`、2×`long const*`、5×`int const*`、
   `float*`、9×`int`、`int const*`），语义未知 ⇒ 从零 replay 需逆推 SASS。
   kit 的 `aot/aot.json` 有 Triton 内核完整签名，但**专家内核不在其中**。
5. **启动阶段不发射专家内核**：ncu connect 后 CSV 一直为空直到发请求，
   故冷 prompt 的第一个专家内核就是 launch #1（对后续定位有用）。
6. `DRY_RUN=1 ./start.sh` 可打印两 rank 完整 docker 命令，**但 service 运行时持 start.lock，
   DRY_RUN 会失败**，必须先停服。镜像 ENTRYPOINT 是 `nvidia_entrypoint.sh`（banner 后 exec "$@"），
   在 CMD 前插工具不需要覆盖 entrypoint。

**事故与根因**：在模型驻留（约 104 GB）下对真实专家内核做 ncu 多 pass kernel replay，
head 节点内存被打爆，sshd banner 超时（LAN 与 CX7 两条链路都是），worker 正常，
**由用户人工拔电源恢复**。GB10 统一内存 ⇒ replay 的 save/restore 就是主机 RAM，
富余仅 5–8 GB，必然 OOM。**方法与该硬件内存结构不相容，不是调参问题。**
我另有两处失误：手动 `docker run` 绕过了 `start.sh` 的 memguard；实验容器未设 `--memory` 硬上限。

**已固化为硬约束**：见 [发现与结论 §0](<01-发现与结论.md>)。
此后驻留态只做无重放观测（system-wide GPU PM 采样 / 引擎自带 profile / metrics），
需要重放一律先停服且工作集限个位数 GB，任何实验容器必须带内存硬上限。

**r1 结论**：**未取得 DRAM 字节数据，2.00× 缺口仍未分离。** 本轮不宣称任何分离结果。

## 2026-11-24 · E-DRAM-01 r2：换零注入路径，2.00× 缺口分离成功

用户重启后先只读复核：两节点 service `active`+`enabled`、容器 Up、`/health` ok，
**head available 8 GB、worker 10 GB**，与用户所说 5–8 GB 富余一致。

**方法换轨**：r1 的 kernel replay 与统一内存结构不相容（§0），改为
**设备级 GPU PM 采样**——`nsys --gpu-metrics-devices`，不注入引擎进程、无重放、
引擎全程由 systemd 照常运行。采样容器 `--memory=2g --memory-swap=2g` 硬上限。
**每一步前后都查 `free -g`，全程稳定 8 GB。** 先跑 3 秒空载 pilot 验证权限与足迹，再放大。

**踩到并解决的三个坑**：
1. 设备被识别为 **GB20B**，metric set 别名是 `gb20y`/`gb20y-top`，不是 `gb10b`；
   host nsys 2025.3.2 与容器 2026.3.1 的别名表不同，**用容器内的**。
2. 默认 General set 只有 19 个计数器、**无内存带宽项**；`gb20y-top` 有 177 个，
   含 `VidL2 Total/Misses from L1TEX`、SysL2、Tensor Pipe、**CS SM Warps Occupancy**。
3. **标着 `[GB/s]` 的字段原始值是 sectors/s**，须 ×32/1e9。
   已知字节 streaming 校准两次：10 kHz 误差 0.184%、5 kHz 0.241%，与频率无关。
   （另：`GPC Frequency [MHz]` 原始值实为 Hz，又一处名不实。）

**一次自我纠正的分析错误**：最初用"DRAM>150 GB/s"找段，得到的高带宽段
**Tensor Active 中位数为 0** ⇒ 那些时刻根本不是专家 MMA。
**用结论选样本是循环论证**，改为按 **Tensor Pipe 活跃度**门控定位 MMA 相位。
但判决本身**不依赖门控**——用整 chunk 形态否证 H1。

**判决**：冷前缀 10755 token、cached 0、prefill 6.376158 s ⇒ 1686.75 tok/s（零注入真实速度）。
