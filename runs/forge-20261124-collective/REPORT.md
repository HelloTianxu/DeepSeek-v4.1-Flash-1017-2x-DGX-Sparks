## 1. 方法与口径

### 1.1 线上字节：RDMA port 计数器（纯 sysfs 只读）

`rdma_sample.py` 高频读两节点 `port_xmit_data / port_rcv_data / *_packets`，
`coll_probe.sh` 在冷前缀请求前后开窗对齐。**不注入引擎、不碰 GPU、不改配置。**

**单位交叉验证**：`port_xmit_data / port_xmit_packets × 4 = 1067.2 B/包`，
与 `active_mtu 1024` + 包头吻合 ⇒ 计数器单位为 **4 octet**。

**采样分辨率陷阱（必须声明）**：实测采样间隔中位 **13.83 ms**（p90 16.49 ms），
而单次 all-reduce 是亚毫秒级。**因此"峰值 9 GB/s"是 14 ms 均值，不是瞬时带宽，
不得据此声称网络跑得慢。** 本方法可靠的产物只有**总字节**与粗粒度活跃分布。

### 1.2 可达带宽：`ib_write_bw` 直接实测（替代线速假设）

缓冲区仅数十 MB，带 `MemAvailable < 5 GiB` 中止闸。GID index 5 = RoCEv2 + IPv4。
两条 rail 分属不同网段：`rocep1s0f1` → 192.168.100.x，`roceP2p1s0f1` → 192.168.101.x。

### 1.3 流量来源分离

同请求抓取全部 metrics 增量：**`kv_shard_copy_bytes` / `kv_shard_moved_bytes` /
`kv_shard_prompt_bytes` 增量全为 0**，`kv_shard_copies/moves` 亦无。
⇒ **这 11+ GB 基本全是 TP collective，不是 KV 搬运。**（`spill_staging_bytes` 29.77 MB 是磁盘侧。）

## 2. 实测：线上字节

| run | MTU | tok | prefill s | tok/s | 线上字节 | KiB/tok |
|---|---|---:|---:|---:|---:|---:|
| A-mtu1024-r1 | 1024 | 10752 | 5.138920 | 2092.27 | 11.7588 GB | 1068.01 |
| A-mtu1024-r2 | 1024 | 10751 | 5.103467 | 2106.61 | 11.7576 GB | 1067.99 |
| B-mtu4096-r2 | 4096 | 10755 | 5.077998 | 2117.96 | 11.2886 GB | 1025.02 |
| B-mtu4096-r3 | 4096 | 10751 | 5.082038 | 2115.49 | 11.2846 GB | 1025.03 |
| B-mtu4096-r4 | 4096 | 10753 | 5.099369 | 2108.69 | 11.2866 GB | 1025.02 |

**每 token 约 1 MiB 的跨机流量。** MTU 4096 下计数少 4.03%，
是**每包头部开销被计入计数器**所致（包数 5,509,459 → 1,428,216，**3.86×**；
均包 1067.3 → 3951.4 B），**不是数学变了**。故真实载荷取 **11.28 GB**（开销最小的一组）。

## 3. 实测：可达带宽与硬件归因

| 配置 | 消息 | 实测 | 换算 |
|---|---|---:|---:|
| MTU1024 单 rail QP=1 | 64 KB–20 MB | 108.7–109.0 Gb/s | 13.6 GB/s |
| MTU1024 单 rail QP=4 | 4 MB | 111.87 Gb/s | **13.98 GB/s** |
| MTU1024 单 rail QP=8 | 4 MB | 111.87 Gb/s | 13.98 GB/s |
| **MTU1024 双 rail 并发** | 4 MB ×2 | 92.59+92.60 Gb/s | **23.15 GB/s 聚合** |
| **MTU4096 单 rail QP=4** | 64 KB–20 MB | **111.87 Gb/s** | **13.98 GB/s** |

**三个判据性事实**：
1. **QP 从 1→4→8 几乎不变**（108.8→111.87）⇒ 不是 QP/并发限制。
2. **64 KB→20 MB 完全平坦** ⇒ 不是消息大小/摊销问题。
3. **MTU 1024 与 4096 完全相同** ⇒ **MTU 不是带宽约束**。

**硬件归因（sysfs 只读）**：网卡 `current_link_speed=32.0 GT/s`、`current_link_width=x4`
⇒ **PCIe Gen5 x4**，裸速率 `4×32×128/130 = 126.0 Gb/s`。
实测 111.87 Gb/s = 裸速率的 **88.8%**（协议开销后的典型值）。

**⇒ 200 Gb/s 光口被主机侧 PCIe Gen5 x4 卡住。这是拓扑事实，不是配置可解项。**
双 rail 聚合 23.15 < 2×13.98=27.96，说明还有共享瓶颈（未进一步分离）。

## 4. 判决：collective 主要是真传输

| 量 | 值 | 来源 |
|---|---:|---|
| 真实载荷 | 11.28 GB | 本轮实测 |
| 可达聚合带宽 | 23.15 GB/s | 本轮 `ib_write_bw` 实测 |
| **纯搬运最短耗时** | **487.4 ms** | 相除 |
| collective 内核时长（按 token 缩放） | 671.7 ms | ledger 0.538977 s × 10752/8628 |
| collective 内核时长（按 chunk 数 6/5 缩放） | 646.8 ms | 同上，另一缩放口径 |
| **非传输部分** | **159.4–184.3 ms** | 差 |
| 占 collective | **24.6–27.4%** | |
| **占 prefill 窗口** | **3.10–3.59%** | |

**若 NCCL 只达实测天花板的 80%**（协议/通道开销），纯搬运需 **609.3 ms**
⇒ 非传输部分**趋近于零**。

**⇒ collective 已接近硬件可达上限，可回收的同步/自旋最多约 184 ms（窗口 3.6%），
也可能几乎没有。Review 说的 6.3–11.0% 不成立。**

### 4.1 Review 错在哪（完整错误链）

1. **字节低估 2.7×**：按「2048 行 × D5120 × bf16 = 20.97 MB/条 × 160–320 条」估 3.4–6.7 GB，
   实测 11.28 GB。**说明实际 all-reduce 条数或 dtype 与模型假设不符**（未进一步分离，不影响判决）。
2. **带宽高估 2.16×**：拿光口标称 200 Gb/s×2 = 50 GB/s 当分母，
   实测可达只有 23.15 GB/s（PCIe Gen5 x4 封顶）。
3. 两个错误**同向叠加**，把「总时间 − 搬运时间」这个差值放大了约 2.5 倍。

**教训：凡「实测总量 − 理论分量 = 可回收量」的推断，两个输入都必须实测，
否则误差会在差值上放大。本轮已用直接测量替代两侧假设。**

## 5. MTU A/B：无收益，已回滚

### 5.1 变更确实生效

两节点两口 MTU 1500→4200，`active_mtu` 1024→**4096**，链路 ACTIVE，两条 rail ping 通。
包数 **3.86× 减少**，均包 1067.3→3951.4 B。**变更本身无疑义。**

### 5.2 端到端无收益

| 对照 | n | 中位 tok/s | 区间 |
|---|---:|---:|---|
| 本轮 A（MTU1024） | 2 | 2099.44 | [2092.27, 2106.61] |
| 本轮 B（MTU4096，剔预热） | 3 | 2115.49 | [2108.69, 2117.96] |
| **历史基线（MTU1024，同探针）** | **8** | **2119.82** | [2102.80, 2122.69] |

**对自己那 2 次 A 比是 +0.76%，对 n=8 历史基线比是 −0.20%。**
**A 组样本太少且恰好偏慢，制造了假阳性。** 以更大样本为准：**MTU 无收益。**

这也与 §3 的机制一致：**瓶颈在 PCIe 不在包速率，减包数自然不涨带宽。**

### 5.3 已回滚并验证

MTU 改回 1500（`active_mtu` 1024），服务经 user systemd 重启，
`/health` ok、`TF_DS_ENGRAM_AIO=0` 基线保持、内存 8.57 GiB。
恢复后稳态 **2103.48 / 2099.71 tok/s**，落在历史基线区间内。
**MTU 为运行时改动、未持久化，重启本来也会自动还原；仓库基线未被污染。**

## 6. 战略含义：剩余杠杆进一步收窄

collective 这条路**基本关闭**：它是真传输，且已贴近 PCIe 决定的硬件上限。
要再降只有两条，都不是本地配置能做的：
1. **减少跨机字节**——改 TP 布局/并行策略（架构级，且每 token 约 1 MiB 是算法决定的）。
2. **更多 PCIe 通道**——硬件改动。

结合 [Review](<../forge-20261124-review/REPORT.md>) 已判死的内核层，
**当前唯一还活着的显著杠杆是 chunk 4096 + CONTEXT 减半（投影 +23.0%，需产品取舍）。**

## 7. 边界

1. **collective 内核时长是跨源缩放**（ledger 8628 tok 探针 → 本轮 10752 tok），
   给了 token 比与 chunk 比两种口径；**不是同请求直接测得**。这是本轮最大的不确定性。
2. 未直接测 NCCL 实际达成带宽，故用 `ib_write_bw` 天花板作上界；
   若 NCCL 效率低于 100%，非传输部分只会更小，**结论方向保守**。
3. `ib_write_bw` 的 MTU1024 组在**引擎驻留态**测、MTU4096 组在**停服态**测，
   内存带宽竞争不同；但两者数值完全相同（111.87），且端到端 A/B 独立佐证，故不影响判决。
4. 双 rail 聚合 23.15 < 2×13.98 的共享瓶颈**未分离**。
5. 全部单流空载；生产多路未复验。worker 侧 GPU 未同期采样。
6. 未测 all-reduce 的实际条数与 dtype，故 §4.1 的字节低估**原因**未定位（不影响判决）。
