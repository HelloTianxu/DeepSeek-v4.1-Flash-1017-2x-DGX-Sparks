# E-SELF-01 · 自研方向一「让 load 保持在飞行中」判决：**无实施空间（基线已有更强形式）**

**来源**：E-ABS-03 §6 提出的两条可借鉴思路之一（上游 `db7364e63`，Nemotron CUDA，位精确）。
**结论**：**不做。** 我方 decode 路径的三类 kernel **早已实现该机制，且形式严格更强**。
本轮先测量定位、再读码核实，避免了一次「实现一个已经存在的东西」的无效开发。

---

## 1. 先定位：decode 一轮的时间花在哪（实测）

上游那个改法针对 router / topk / add_moe_norm。**先确认这些在我方 decode 里占多少**，
否则可能去优化一个占比 2% 的靶子。

**方法**：`RANK1_PROFILE=1` + `TF_DS_CLOCK_MARKS=1`，跑 N=1 decode 探针，
读 rank1 的 `round_clock_us`（每阶段 [µs/轮, 次/轮]）。

**两个操作要点（已入手册）**：
- profile 输出在**退出时**才打印（`lanes_main.zig:231` defer），且停服流程会**重建容器**，
  `docker logs` 拿不到。必须去 **worker 的 `~/.cache/dsv41-tensorfold/logs/*rank1.log.gz` 归档**里取。
- `TF_DS_CLOCK_MARKS=1` 会在 graph 内也打点，**打断 PDL 链，绝对值偏大**。
  实测该轮 N=1 **58.621**（基线 59.1，−0.8%）。**只看相对占比，绝对值不可当基线。**

**结果**（rank1，762 轮）：

| 阶段 | µs/轮 | 次/轮 | 说明 |
|---|---:|---:|---|
| **moe** | **12909.0** | 33 | **绝对大头** |
| a_q | 2196.5 | 34 | q 投影（稠密 EXL3 linear） |
| a_in | 1911.8 | 34 | attention 输入 |
| attn | 1506.2 | 33 | |
| sh_rows | 1162.2 | 32 | KV 分片行交换 |
| a_woa | 915.4 | 34 | |
| a_core | 661.9 | 34 | |
| **m_rt（路由）** | **629.9** | 33 | **仅 moe 的 4.9%** |
| gather_m | 501.7 | 33 | |
| engram | 450.1 | 2 | |

注：stretch 总段与 `a_*`/`sh_*` 细标记是两套口径，**不可直接相加**（会重复计数）。
但无论哪种口径，**moe 都是第一大项**（stretch 口径 78.2%，全加口径 54.9%）。
`m_gu` / `m_x` 计数为 0——它们是 TP4 2D MoE 路径的标记，我方 TP2 不走。

**第一个判决**：**照搬 Nemotron 改 router/topk，靶子只有整轮的约 2%**
（m_rt 629.9 µs ÷ 整轮约 34 ms）。即便全部消灭也不值得。**方向必须重定位到专家核心与稠密 linear。**

## 2. 再读码：我方 kernel 是否已有「loads in flight」

### 2.1 稠密 decode linear：`lane_gemv.cu`

| 证据 | 位置 | 内容 |
|---|---|---|
| 流水级数 | `lane_gemv.cu:196` | `gemv_kernel<64, 64, 8>` → **STAGES = 8** |
| 异步拷贝 | `qmm_frag.cuh:31` | `cp.async.cg.shared.global [%0], [%1], 16` |
| 预灌 | `lane_gemv.cu:108-117` | 主循环前灌满 **STAGES-1 = 7** 级权重与 x，各自 `commit()` |
| 跨迭代重叠 | `lane_gemv.cu:120-128` | `wait<STAGES-2>()` 后**先发起第 `it+7` 级 load_x/load_w，再算本级** |
| 单次多 load | `:78-92` | XC/WC/SC 三组 `#pragma unroll`，每级一次发出多个 16B 异步拷贝 |

### 2.2 专家核心与分组 GEMM

- `experts.cuh:23-31`：同样 `cp.async.cg.shared.global` 16B + `cp.async.commit_group` + `cp.async.wait_group`
- `experts.cu:279`：`expert_kernel<64, 1, EPI, 2, 4>`
- `qmm_group.cu:340`：`group_kernel<64, 16, 64, 1, 4, 8, ...>` → **8 级**

### 2.3 机制对比：我方形式更强

| | 上游 `db7364e63`（Nemotron） | 我方基线 |
|---|---|---|
|  staging 目标 | **寄存器**（`y[MTE][MAXS]`, `xv[MTE]`） | **共享内存多级缓冲** |
| 发射时机 | 本 kernel 内所有 load 一次性发出，再算 | 每级多个 cp.async，**提前 7 级** |
| 跨迭代重叠 | **无** | **有**（算第 it 级时第 it+7 级在飞） |
| 线程数手法 | NT → MT=1024 提高在飞 load 数 | 128 线程 × 多级 × 每级多 load |
| 位精确保障 | shared memory + 原线程映射还原求和顺序 | 注释即 "retains K-slice order"，同口径 |

**上游补的是「原本没有流水的 kernel」；我方这些 kernel 本来就有，而且是更先进的 cp.async 多级软件流水。
故无实施空间，判决不做。**

## 3. 顺带纠正一个必须纠正的混淆

E-ROOF-01 的 **2.00× 缺口是 prefill 的，不是 decode 的**：
其口径为 R2048、chunk 2048、core 中位 20.162 ms、对应 1735 tok/s，M̄=32。
**decode 每轮仅约 2 行、每 token 选 6/384 专家，M̄ ≈ 0.03，是完全不同的 regime。**
把 prefill 的 2× 缺口当 decode 的可回收上界是错的。

### decode MoE 的屋顶距离（**估算，非实测 DRAM 流量**）

按我方归档几何（E-ROOF-01 §3：E=384, D=5120, I=1152 为 TP2 本地；每 token 6 专家）：

| 量 | 值 | 依据 |
|---|---:|---|
| 每专家字节 | 6.414 MB | 3 × 5120 × 1152 × 2.9/8 |
| 每层专家激活 | ≈12 | 2 行 × 6 专家，去重后 ≈11.9 |
| MoE 层数 | 33 | 本轮 profile 计数 |
| 每轮唯一专家字节 | **≈2.540 GB** | 33 × 12 × 6.414 MB |
| 带宽屋顶最短耗时 | **≈10.32 ms** | 2.540 GB ÷ 246.2 GB/s |
| 实测 moe（profile 偏大） | 12.909 ms | 本轮 |
| 比值 | **≈1.25×** | 即约 **80% 屋顶** |

**假设明示**：2 行/轮（DRAFTS=1）、6 专家/token、2.9 bpw、忽略 scale/bias 与可能的 tile 重读。
**这是推导估算，不是 ncu 实测流量**，不可当判决性证据。
但方向清楚：**decode MoE 已接近带宽饱和，MLP 类改造空间有限**；
而 prefill 的 50% 缺口若源于 tile 重读，则对应的是**另一条思路（每权重一窗口只读一次）**。

## 4. 方法论收获（已入手册）

**移植异后端思路前，必须先做「机制同构核查」**：
不是问「我方有没有这个 commit」，而是问「**我方 kernel 有没有这个机制，是什么形式，孰强孰弱**」。
本轮若跳过这一步直接动手，就会花数小时实现一个基线已有、且已被更强形式覆盖的东西。

**顺序必须是：先测量定位靶子大小 → 再读码核实机制是否已存在 → 才谈实现。**
本轮第一步就把靶子从「router/topk」纠正到「专家核心」（占比 2% → 78%），
第二步就发现该机制已存在。**两步都发生在写任何代码之前。**

## 5. 仍然开放的真问题

E-ROOF-01 §4 的两个竞争假设**至今未分离**，这才是 prefill 侧的关键：
1. 实际 DRAM 流量 ≈ 2× 唯一字节（tile 重读）→ 已在屋顶，可回收的是「消除重读」
2. 融合内核效率低 → 距屋顶一倍，属实现问题

**本轮证据倾向于排除「decode 侧 MLP 不足」这一支**（已有 7 级流水 + 接近屋顶估算）。
分离仍需 ncu `dram__bytes_read.sum`，且**必须在停服态做独立 replay**
（驻留态 ncu kernel replay 已验证会爆内存，见手册死路清单）。

## 6. 更正批注（2026-11-24，项目整理时发现；原文保留不改）

**本报告 §3 与 §5 有两处错误，均因只读了 E-ROOF-01 而未核对实验索引。以本批注为准。**

### 6.1 「两假设至今未分离」——错。早已分离。

`runs/forge-20261123-dram/REPORT.md`（**E-DRAM-01 r2**，零注入设备级 PM 采样，引擎照常运行）
已完成分离，且结论写在 `docs/performance/03-实验与证据索引.md` §1c：

- **H1（tile 重读打到 DRAM、已在屋顶）被否证**。H1 的定量预测是专家核心占 chunk 42.8% 的时间里
  DRAM 必须贴近 246 GB/s；实测最大 chunk 941.6 ms 内 DRAM 均值仅 **121.5 GB/s = 屋顶 49.3%**，
  >200 GB/s 仅占时 **9.8%**，最长高带宽段 3.6 ms，众数落在 140–160 档。**H1 要求的形态不存在。**
- **H2（内核效率缺口）成立**。123.1 GB/s 基本就是真实 DRAM 带宽。
- **重读是真的，但被 L2 吸收**（L2 请求 742.2 GB/s = 6.43×，读命中率 **84.5%**），
  **没有变成 DRAM 流量**——这正是 H1 推理链断掉的地方。

**故 §5「仍开放的真问题」应改为：缺口性质已定，开放的是具体 stall 根因。**

### 6.2 「无实施空间」——判漏了一半。机制是低占用延迟受限。

E-DRAM-01 r2 §5 实测：Tensor>20% 相位里三条饱和度**同时都低**
（DRAM 46.9%、SM Issue 36.2%、Tensor Pipe 37.0%），而 **Occupancy 中位数只有 17%**。
原文判词：**「在飞的内存请求不够多，盖不住延迟」**——**这是延迟受限，不是带宽受限。**

静态限制因子（与实测吻合）：

| 内核 | regs/thread | threads/block | shared | 驻留上界 |
|---|---:|---:|---:|---|
| **down** | **255** | 128 | — | **8/48 warps = 16.7%** |
| gateup | 106 | 256 | 44288 B | 16/48 = 33% |

**所以 §2 的结论只对了一半**：
- **对的部分**：我方确实已有 cp.async 多级流水，形式强于上游的寄存器 staging，
  「再加一层流水」没有意义。
- **判漏的部分**：**「有流水」≠「在飞请求够多」**。占用率 17% 意味着驻留 warp 太少，
  即便每 warp 有 7 级流水，**总在飞请求数仍不足以盖住延迟**。
  上游那个改法的**另一半——把线程数 NT 提到 MT=1024**——正是治这个的，
  而我方 `down` 的瓶颈是 **255 regs/thread**，属**寄存器压力**，不是流水级数。

**修正后的判决**：
「照搬上游给 router/topk 加 staging」仍然否决（靶子只占整轮 2%，且已有流水）。
但**「提高专家内核占用率」是一个真实、未被否证的自研方向**，
方向是**降寄存器压力 / 调 block 形状**，而非加流水。

**注意口径**：E-DRAM-01 的占用率与饱和度测的是 **prefill**（chunk 941.6 ms、专家核心）。
**decode 的占用率未测**，不可直接搬用；本报告 §3 的 decode MoE ≈80% 屋顶仍是估算。
若要立 decode 的占用率结论，需另测。
