# E-ROOF-01：实测 GB10 roofline 分母，专家核心判为带宽侧且距屋顶 2.00×

日期 2026-11-23，Asia/Shanghai。**经用户明确授权停服测试**（"这个TP2环境你可以停服测试，现在没有在使用。注意，只要不破坏推理环境就可以"）。
停服前快照与恢复路径先落盘于 [RESTORE.md](<RESTORE.md>)；测后已 `systemctl --user start` 恢复，
`is-active=active`、容器 `dsv41-1017-exl3-tf` Up、`/health` 返回 `{"status": "ok"}`。
**未改配置、镜像、模型、unit 限制，未杀外部进程。**

本轮补的正是 [发现与结论 §4](<../../docs/performance/01-发现与结论.md>) 写明缺失的分母：
"实际DRAM字节、执行FLOP、动态解码指令和同格式可持续吞吐均缺失"。
本轮拿到**同格式可持续吞吐**与**硬件两个屋顶**，因此第一次能把专家核心放到 roofline 上判决。

## 1. 方法与口径

同镜像 `tensorfold-dsv41:exl3-tp2-8348338a8d90` 起 `--rm` 临时容器（`--gpus all --ipc=host`），
torch 2.13.0a0+9186a08b2c.nv26.07，CUDA event 计时，warm 5 / reps 12–20，每次 synchronize。
设备：**NVIDIA GB10，SM 12.1，48 SM，L2 = 24 MB**，total 124544 MB。

- r1 **作废**：FLOP 按 gate+up+down 三矩阵 `6*D*I` 计，却只分配两个权重矩阵，TFLOPS 虚高 1.5×。
  断言 `wbytes == 3*E*D*I*2` 在 r2 加上并通过。r1 数据保留为 `roofline-r1.json`。
- **r2 权威**：`roofline-r2.json`。gate+up 合并 `(E,D,2I)`、down `(E,I,D)`，与 FLOP 口径一致。
- 同缓冲重复读在工作集 ≤ L2 时测的是**缓存带宽不是 DRAM**，已单列标注。
- bmm 用 FP16 权重，字节是 EXL3 2.9bpw 的约 5.5×，**其 GB/s 不可与生产内核直接比**，
  只用于形状/摊销趋势与"同形状能达到的带宽"参照。

## 2. 硬件两个屋顶（实测）

| 项 | 实测 | 官方 | 达成 |
|---|---:|---:|---:|
| DRAM 可持续读（67.11MB 工作集） | **246.2 GB/s** | 273 GB/s | **90.2%** |
| DRAM 可持续读（8589.93MB 工作集） | 241.0 GB/s | 273 | 88.3% |
| FP16 稠密 GEMM 16384³ | **100.82 TFLOPS** | — | — |
| FP16 稠密 GEMM 8192³ | 98.41 TFLOPS | — | — |
| FP16 稠密 GEMM 4096³ | 92.33 TFLOPS | — | — |

**机器平衡 = 100.82e12 / 246.2e9 = 409.4 FLOP/byte。**

L2 驻留参照（**不是 DRAM**）：25.03MB → 502.1 GB/s；8.26MB → 715.0 GB/s。

## 3. 真实专家形状：时间对 M 几乎不敏感 ⇒ 权重带宽主导

`E=384, D=5120, I=1152`（TP2 head 本地），FP16 权重恒 13.59 GB：

| M/专家 | 耗时 ms | TFLOPS | 权重 GB/s | AI | roofline 侧 |
|---:|---:|---:|---:|---:|---|
| 2 | 58.120 | 0.47 | 233.8 | 2.0 | 带宽 |
| 4 | 56.031 | 0.97 | 242.5 | 4.0 | 带宽 |
| 8 | 58.425 | 1.86 | 232.6 | 8.0 | 带宽 |
| 16 | 58.433 | 3.72 | 232.6 | 16.0 | 带宽 |
| **32** | **60.426** | 7.20 | **224.9** | 32.0 | 带宽 |
| 64 | 60.796 | 14.31 | 223.5 | 64.0 | 带宽 |
| 128 | 66.012 | 26.35 | 205.9 | 128.0 | 带宽 |
| 256 | 80.357 | 43.29 | 169.1 | 256.0 | 带宽 |

**M 从 2 到 64（32 倍）耗时只从 58.120 到 60.796 ms（+4.6%）。**
这是权重读主导的判据性特征。M=32 时权重带宽 224.9 GB/s = 实测 DRAM 峰值的 **91.3%**，
即**同形状的普通 FP16 grouped GEMM 已经贴着带宽屋顶**。

真实路由下 M̄ = R×6/384：R2048→32、R436→6.8、R128→2。**全部落在带宽侧。**

## 4. 判决：专家核心是带宽侧，且距屋顶 2.00×

用归档的生产口径（[ledger](<../forge-20261123-bottleneck-ledger/ledger.json>)、
[REPORT §2/§5](<../forge-20261123-bottleneck-ledger/REPORT.md>)）：
R2048 有效 FLOP = 14336 pairs × 35389440 = **507.3 GFLOP**；
TP2 每 rank 每层唯一专家字节 **2.482 GB**；core 中位 **20.162 ms**。

| 量 | 值 | 含义 |
|---|---:|---|
| 有效算术强度 | **204.4 FLOP/byte** | < 机器平衡 409.4 ⇒ **带宽侧** |
| 唯一字节 / 时间 | **123.1 GB/s** | 仅实测 DRAM 峰值的 **50.0%** |
| 带宽屋顶最短耗时 | **10.08 ms** | 2.482 GB ÷ 246.2 GB/s |
| 实测 / 屋顶 | **2.00×** | **首次用实测分母给出的可回收上界** |

**结论：算力不是专家核心的绑定约束。** 真实 SASS 是 HMMA.16816.F32（FP16 输入/FP32 累加），
而该形状的算术强度只有机器平衡的一半，**算力屋顶根本碰不到**。

**2.00× 缺口的两种竞争解释，本轮仍未分离**（不得择优）：
1. 实际 DRAM 流量 ≈ 2× 唯一字节（tile 重读）。若成立则**已在 DRAM 屋顶**，
   可回收的是"消除重读"，不是"提高带宽利用率"。
2. 融合解码内核效率低于普通 GEMM。若成立则 123.1 GB/s 是真实流量，
   距屋顶还有一倍，属内核实现问题。

分离仍需 ncu 的 `dram__bytes` 与 `sm__inst_executed`（此前权限被拒），
或一个固定 input/pick/权重的原样 replay。**本轮未做，不宣称已唯一识别。**

## 5. 跨机对照：算力赢 4.2×，带宽反而输

**只比硬件同类实测量，不搬 Mac 的端到端结论**（遵循 §8 "不移植Mac屋顶线"）。
Mac 数字取自熔炉项目归档 `experiments/execution/forge-realize-20261123-r4/realize.json`。

| | Mac M3 Ultra | 单 GB10 | 双 Spark TP2 |
|---|---:|---:|---:|
| 官方带宽 | 819 GB/s | 273 GB/s | 546 GB/s |
| **实测流式读** | **707.9 GB/s** | **246.2 GB/s** | **492.4 GB/s**（各读半份后聚合） |
| **实测稠密 GEMM** | **23.92 TFLOPS** | **100.82 TFLOPS** | 201.6 TFLOPS |

**算力 4.21×，带宽 0.696×。** 由于 prefill 最大单项（专家 core 38.38%）在带宽侧，
**"算力比 Mac 高两倍多"这个前提对当前 prefill 不成立**——
它落在带宽侧，而双 Spark 的聚合带宽比单台 Mac Studio 还低 30.4%。

两机 prefill 绝对值（Spark ~1735、Mac 生产 ~1212 tok/s）**不可直接归因于本表**：
量化格式（EXL3 2.9bpw vs oQ4e）、chunk、有效层数、TP 布局都不同，
跨机端到端比较需先对齐算法（本项目既有纪律）。本表只用于回答"算力优势能否用上"。

## 6. 由 roofline 直接导出的杠杆：加大 chunk（条件投影，未验证）

既然专家耗时对 M 几乎不敏感，**每 token 的专家成本 ≈ 权重读 ÷ M**。
M=32→128（chunk 2048→8192）：耗时 60.426→66.012 ms（**+9.2%**）而 token 数 ×4
⇒ **每 token 专家成本 ÷3.66**。

按生产 R2048 的 20.162 ms 乘同一 M 比例（1.0924）作条件投影：

| 项 | 当前 chunk2048 | 投影 chunk8192 |
|---|---:|---:|
| bulk 调用 | 80 × 20.162 = 1612.96 ms | 20 × 22.03 = 440.6 ms |
| R436 | 20 × 9.733 = 194.7 ms | 194.7 ms（不变） |
| R128 replay | 20 × 4.973 = 99.5 ms | 99.5 ms（不变） |
| 专家 core 合计 | ≈1908.5 ms | ≈**734.8 ms** |
| kernel 窗口 | 4972.65 ms | ≈**3798.9 ms** |
| 对应 tok/s | 1735.09 | ≈**2271** |

**这是"其他分类不变"的反事实投影，不是实测收益、不是上界。**
加大 chunk 同时会改变 collective 次数、attention/HC 形状、激活与 KV 峰值内存，
必须单变量 A/B 实测才能算收益（本项目既有纪律：不按比例连乘）。

**阻塞点已核实**：`zig/patches/0008-pool-window.patch` 中 `pub const chunk_rows = 2048;`
是**编译期常量**；出厂引擎 `tensorfold-native` 的 strings 里
**没有 `TF_DS_PREFILL_CHUNK`**（只有 `TF_DS_PREFILL_INTERLEAVE_MS`、`TF_DS_PROMPT_GEMM_ROWS`、
`TF_DS_PROMPT_WINDOW_ROWS`、`TF_DS_PLAIN_ROWS`、`TF_DS_REPLAY_FLOOR`、`TF_DS_ROUND_ROWS`）。
patch 注释提到该 env，但**出厂二进制不支持** ⇒ **调 chunk 必须改 patch 并重编译引擎**。
按项目规则，超过一分钟的构建须先报预计时长并获确认，本轮**未构建**。

## 7. 本轮边界

- 未测实际 DRAM 字节与执行 FLOP，2.00× 缺口的两种解释未分离。
- bmm 是 cuBLAS FP16 稠密路径，**不是 EXL3 融合解码内核**，其绝对耗时不可当生产可达值。
- chunk 投影是条件反事实，未 A/B。
- 未做 worker（rank1）同期测量，双 rank 聚合带宽 492.4 GB/s 是"各读半份"的算术聚合，非实测合计。
- 停服窗口测得，无模型驻留；生产环境的带宽可用量可能因 KV/Engram 流量而更低。
