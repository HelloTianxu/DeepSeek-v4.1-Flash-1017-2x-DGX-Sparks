# E-DECODE-01：Decode 现状实测与优化空间

> **判决：decode 与 prefill 性质相反——它已经基本吃满带宽。
> 实测 DRAM 均值 203.9 GB/s = 屋顶 82.8%、中位 220.9 = 89.7%。
> 剩余空间约 +20%（110 → 133 tok/s），不是 prefill 那种 2×。**
>
> **并且「100 vs 30–40」的口径谜团解开了：两个数是同一系统的不同口径，不存在神秘缺口。**

全程内存安全：最低 6.96 GiB（PM 采样容器带 `--memory=2g` 硬上限），未停服、未改配置。

---

## 0. 口径谜团：没有缺口

| 并发 | 聚合 tok/s | **每路 tok/s** | 批/s | tok/轮 | MTP 接受率 |
|---|---:|---:|---:|---:|---:|
| N=1 greedy | **61.4** | 61.4 | 30.0 | 2.048 | 58.5% |
| N=1 temp1.0 | 57.4 | 57.4 | 30.0 | 1.910 | 52.8% |
| N=2 greedy | **83.1** | **41.5** | 20.4 | 2.040 | 61.2% |
| N=4 greedy | **110.0** | **27.5** | 14.5 | 1.896 | 68.9% |
| N=4 / 700tok 长跑 | 109.3 | 27.3 | — | 1.907 | 67.9% |

**用户说的「两台能到 100」= N=4 聚合 110；「实际只有 30、40」= N=4 每路 27.5 / N=2 每路 41.5。**
同一系统、同一配置，**两个口径**。此外 N=1 的**轮速恰好 30.0 轮/s**，也落在"30"上。

口径定义（本轮统一）：`decode_tok_s = generation_tokens_total增量 / request_decode_seconds_sum增量`，
不含 prefill；聚合口径用 wall。首次请求偏低已剔除。

## 1. 决定性测量：decode 真的把带宽吃满了

设备级 GPU PM 采样（复用 E-DRAM-01 r2 已验证安全路径：独立容器、`--memory=2g` 硬上限、
**无内核重放、不注入引擎**）。窗口 4–28 s，n=119988 采样点。
口径沿用已校准换算：`VidL2 Misses from L1TEX` 原始值为 sectors/s，GB/s = raw×32/1e9。

| 指标 | 均值 | 中位 | p90 | 最大 |
|---|---:|---:|---:|---:|
| **DRAM GB/s** | **203.9** | **220.9** | — | 262.0 |
| **占屋顶 246.2** | **82.8%** | **89.7%** | — | 106% |
| L2 请求 GB/s | 301.8 | 285.1 | 447.5 | 638.0 |
| L2 命中率 % | 30.5 | 16.0 | 75 | 100 |
| GR 引擎活跃 % | **95.0** | **100** | 100 | 100 |
| SM Tensor 管线 % | **13.1** | 14.0 | 19 | 28 |
| SM Issue % | 26.2 | 28.0 | 37 | 51 |

- **71.6% 的时间 DRAM > 200 GB/s，39.1% 的时间 > 230 GB/s。**
- L2 请求/DRAM = **1.48**，命中率中位仅 16% ⇒ **几乎没有被 L2 吸收，请求基本直达 DRAM。**
- Tensor 管线只有 13.1% ⇒ **确实不是算力侧**，用户"decode 是带宽型的"判断正确。

**与 prefill 对照（同一屋顶、同一换算）**：

| 相位 | DRAM 均值 | 占屋顶 |
|---|---:|---:|
| prefill（E-DRAM-01 r2） | 121.5 GB/s | **49.3%** |
| **decode（本轮）** | **203.9 GB/s** | **82.8%** |

⇒ **prefill 的一半带宽是内核效率缺口（可回收）；decode 的 82.8% 已接近物理极限。
把 prefill 的"还有 2×"直觉搬到 decode 是错的。**

## 2. 字节账：每 token 1.87 GB，attention 占大头

从 checkpoint 真实张量尺寸算（TP2 切分，排除未加载的 vision/aligner）：

**单 token 独跑，每 rank 4.114 GB**：

| 项 | GB | 占比 | 是否随 batch 摊薄 |
|---|---:|---:|---|
| routed 专家（40层×6×6.38MB） | 1.532 | 37.2% | **否，并集随 token 增长** |
| attn/dense 等 | 1.932 | 47.0% | **是，每批只读一次** |
| shared 专家 | 0.402 | 9.8% | 是 |
| head | 0.248 | 6.0% | 是 |

**实测 N=4 每 token 仅 1.866 GB**（203.9 GB/s ÷ 109.3 tok/s），
因为 2.58 GB 的非专家字节被 4 路 × 1.907 token = 7.63 token 摊薄。

**自洽校验**：每批 68.9 ms × 203.9 GB/s = 14.05 GB；扣非专家 2.58 ⇒ 专家 11.47 GB
⇒ 每层实际并集 **44.9 个专家**（独立路由模型预测 61.6）。
⇒ **真实路由有相关性，并集比独立假设小 27%**。这也是 MTP 划算的原因：
草稿 token 与前序 token 路由相近，验证它们几乎不多读权重。

## 3. 天花板：还有多少

| 口径 | tok/s | 相对当前 |
|---|---:|---:|
| 当前 N=4 实测 | **110.0** | 1.00× |
| 当前字节下打满屋顶（246.2/203.9） | **132.8** | **+20.7%** |
| 绝对渐近（专家零共享，每 token 1.531 GB） | 160.8 | +46.2% |

**+20.7% 是现实上限**（把 82.8% 推到 100%）。
+46.2% 需要 batch 大到专家共享趋零，**被 kit 的 16 行内核上限挡住**（见 §4）。

## 4. 杠杆逐项（含两个查死的）

**① MTP 接受率 —— 唯一"免费"的杠杆，但没有直接旋钮。**
验证前向读的字节与草稿是否被接受**无关**，所以接受率↑ = 同样字节出更多 token。
N=4 接受率 68.9%，若到 90% ⇒ tok/轮 1.896→2.203，**+16% 且零额外字节**。
但深度由 confidence head 自适应决定：

```zig
/// MultiDecoder._depth: the most drafts a stream verifies in a round of `live` streams
/// (TF_DS_PARALLEL_DEPTH unset: 5, 5, 3, 3), at most ... (max_rows / live - 1)
```

N=4 时上限 = 16/4−1 = **3**，实测均 1.336 ⇒ **当前不是上限在卡，是 confidence 在卡**。
`TF_DS_PARALLEL_DEPTH` 可改档但抬高的上限用不上。**无现成旋钮。**

**② ❌ `DRAFTS` 调大 —— 查死，它是布尔不是计数。**
`native.zig:99 drafts: bool`、`model.zig:64 drafts: bool = true`。
模型 `num_nextn_predict_layers = 3`，而 `weights.zig` 是
`for (0..c.draft_layers)` **无条件加载全部 3 块**（约 3.37 GiB/rank 已驻留）。
`DRAFTS=1` 只是"启用 drafter"，**没有"调到 2/3"这回事**。

**③ ROUND_ROWS 16→32 —— 真实杠杆，但被上游 kit 挡住。**
`PORT-RECIPE.md:343`：*"17..32 variants (`ROUND_ROWS=32` in one launch) are a later `KIT_REF` change"*。
提高后 N=4 深度上限从 3 升到 7，才可能让 confidence 放出更多草稿。
`round.zig:40 max_rows = 48`（四节点 lane 用 48），**我们的 pin 只有 ≤16 行内核**。
⇒ **需要换 KIT_REF，不是本地配置能解。**

**④ PARALLEL 调整 —— 是取舍不是提升。**
N=2 每路 41.5 / 聚合 83.1；N=4 每路 27.5 / 聚合 110.0。
提高 PARALLEL 不吃内存（流从既有 POOL 取），但按
`prompt + max_tokens + ROUND_ROWS + 2` 预留，**每路可用上下文按比例缩小**。
且受 16 行上限，N≥5 时深度上限降到 ≤2。**聚合收益递减明显**（+21.7 → +26.9 跨两档）。

**⑤ 降 bpw 减字节 —— 质量代价，未评估。** 每 token 字节直接决定 decode 速度，
2.9bpw 再降会动质量，不在本轮范围。

## 5. 边界与未做

- **长上下文那组作废**：用重复文本（"The quick brown fox…"×1400）导致接受率虚高到
  3.23 tok/轮、且第二次命中前缀缓存（prefill 5.78 s → 0.92 s）。**不能作为长上下文结论。**
  真实长上下文下 KV 读取的影响**未测**（sliding_window=128 + 压缩平面，预期不大但无数据）。
- 源码 ref **f77d5a1 ≠ 生产 pin fbbc9713**，`depth()`/`drafts: bool`/加载结构仅供定性；
  `drafts` 布尔与全部 3 块驻留的结论与 `weights.zig` 无 `drafts` 门控一致，但未在生产 pin 复核。
- DRAM 口径是 **L2 misses 上界**（GB10 另有 SysL2），与 E-DRAM-01 同一保守方向：
  真实 DRAM 可能略低于 203.9，**只会让"已接近屋顶"的结论更强，不会反转**。
- worker（rank1）GPU 侧未同期采样。
- 未测 N=3、N≥5；未做 `TF_DS_PARALLEL_DEPTH` A/B（判断其用不上，未实证）。
- **未停服、未改任何配置、未做写操作。**
