# E-SELF-09：把杠杆推到底 —— 六个候选逐个否证，卡口收敛到 staging 往返本身

- 日期：2026-11-25
- 触发：用户「开搞！」（批准 E-SELF-08 结论后的下一步：把同一杠杆推到底，榨在飞字节）
- 前置：E-SELF-08 已证卡口是「片内递货」，不是 warp 数、不是 DRAM 容量
- **结论：还没到硬件瓶颈。** 读同样字节的纯读只要 **15.877 ms**，mma2 要 **22.70 ms**（1.43×）。
  差 **6.8 ms**，其中**算术只占 0.76 ms**，**6.06 ms 全在 cp.async→shared→栅栏→读回这条 staging 往返上**。
  该往返自己的 stall 是 **barrier 43.8% + long_scoreboard 43.6%**，bank 冲突 0，无一子系统饱和。

## 0. 六个候选，全部用反向干预否证

| 候选 | 干预 | 结果 | 判定 |
|---|---|---|---|

## 2. 形状屋顶标定（三内核读相同字节，只差形状）

| 内核 | 字节 | 耗时(min) | 达成带宽 |
|---|---:|---:|---:|
| stream 顺序流式 | 1.586 GiB | 7.298 ms | **233.4 GB/s**（屋顶复标） |
| pattern mma2 真实跨距 | 3.428 GiB | 14.509 ms | **253.7 GB/s** |
| slab 每程序连续 | 3.428 GiB | 14.525 ms | 253.4 GB/s（**0.999×**） |
| **full 权重+激活** | **6.356 GiB** | **15.877 ms** | **429.8 GB/s** |

- 跨距形状（每程序 320 块 × 1536 B，块间跨距 13824 B）**不比连续慢**⇒ 布局不是卡口，改布局零收益。
- full 带宽 429.8 > DRAM 屋顶，因为激活唯一数据只 0.273 GiB 却被 9 个列块各读一遍，**L2 承接了重复**。

> **⚠️ 我自己犯的错（当场纠正）**：第一版屋顶只搬权重 3.428 GiB，**漏掉激活 staging 2.928 GiB（占 46%）**，
> 却拿 mma2 的完整耗时去比，得出「mma2 只到形状屋顶 64%」的错误结论。
> 补齐激活后正确口径是 **1.43×（效率 70%）**。教训见手册 §7.13。

| 其余各项 | ≤2.9% |
| **shared bank 冲突 ld/st** | **0 / 0** |

**87.4% 的 warp 延迟就是「等 stage 落地」+「在栅栏上等齐」。** 无 bank 冲突、无子系统饱和。

> MODE 3 的 `ldsm=0`、`shared_ld=46.6 M`：编译器把只用 `a[0]` 的 ldmatrix 降级成普通 shared 读。
>
> **⚠️ 更正批注（E-SELF-11）：上面这句解释错误。** `ldmatrix_x4`（原件 `:580-585`）是 **`asm volatile`**，
> 编译器不可能把它「降级成普通 shared 读」。真因是 **sink 链被死代码消除**：兜底只写 `acc[0][0][0]`，
> 无 MMA 时编译器把 acc 折成常量 ⇒ `m2_sink` 判死 ⇒ 操作数全死 ⇒ **nvcc 在输出全死时连 `asm volatile` 一并删除**。
> SASS 实证：MODE 8 的 `LDSM=0` 而 `LDS` 与 MODE 0 **逐个相等（154）**——是删除，不是替换。
> 另：本节「MINB=2 真拿到 2 blocks 却更慢」**存在混淆**，S=4/KB=4 的 shared 61440 容不下 2 block
> （需 122880 > optin 101376），该占用率读数只能来自 S=3,MINB=2，与 S=3 自身 −1.3% 绑在一起。
> 详见 `runs/forge-20261125-self-decouple/REPORT.md` §1、§7。
> 所以 MODE 3 是「环+shared 写+栅栏+**最小**读回」，比原计划的「保留完整 ldmatrix」**更干净**——
> 它证明即便几乎不读回，仍要 21.93 ms。
> 另：`shared_op_st wavefronts` 只 22,464，**cp.async 的 shared 写在 GB10 又一处计数器盲区**，不可据此说没写。

## 4. 当下的单点卡口表述

**8 warps/SM 下，cp.async staging 环的时间覆盖不足**：
每个 stage 由 256 线程发出约 768 个 16 B chunk，然后**全 block 栅栏等齐**，再消费。
warp 有 43.6% 的时间在等全局内存落地、43.8% 在栅栏上等最慢的 warp。

**但为什么加级数（S=5,6）与加 block（2 blocks）都不解决，尚未解释。** 这是本轮留下的**唯一未决机制问题**。
两个待检假设（**均未验证，不得当结论**）：
1. **发射点被栅栏门控**：下一 stage 的 load 只能在全体 warp 过栅栏后才发出，故深度加不上去；
2. **每 stage 的 chunk 数太少**（768 个 16 B），单 stage 的在飞字节不足以覆盖延迟，而这与 S 无关。

**下一步判决实验**（按判决力）：
- 把 `cp_async16` 换成更宽的搬运（若源码支持）或提高每 stage 的 KB 同时保持 shared 不变 → 分离「chunk 数」与「级数」；
- 去掉 stage 栅栏、改用 per-warp 独立环（每 warp 自己的 buffer，无全 block 同步）→ 直接检验假设 1；
- 测 MODE 3 在 2 blocks 下的 stall 是否仍 barrier 主导 → 检验假设 2。

## 4b. 追加判决（E-SELF-09e）：两个假设双双否证，卡口是 shared 往返 + MIO 队列

用户批准继续后，直接摘掉环里的同步做**只计时探针**（MODE 4/5，**故意产生竞态、结果不对，
但指令数与访存字节不变**，故时长有效；绝不可上线）：

| 臂 | min 耗时 | 相对完整 |
|---|---:|---:|
| MODE 0 完整 | 22.754 ms | — |
| **MODE 4 摘掉全 block 栅栏** | **22.959 ms** | **+0.9%（更慢）** |
| **MODE 5 摘掉栅栏 + cp_async_wait** | **21.884 ms** | **−3.8%** |
| 纯读屋顶 | 15.877 ms | −30% |

**假设①（发射被栅栏门控）否证**：摘栅栏零收益甚至更慢。
**假设②（每 stage 在飞字节不足）此前已被 KB=8 否证**（字节/stage 翻倍、在飞更多，时长不变）。

**未跳过工作的证据**：MODE 5 总指令 **2,748,440,286** vs 完整 2,758,024,926（−0.3%）；
L2 读 10.184 vs 10.567 GiB（−3.6%）。

**等待只是换了位置**（MODE 5 ncu，身份 `<2,6,6,64,0,1,5,4>` ✓）：

| stall | 完整 | MODE 5 |
|---|---:|---:|
| barrier | 21.6% | **0.7%** |
| **short_scoreboard（shared 依赖）** | 4.4% | **21.1%** |
| **mio_throttle（MIO 队列满）** | 0.9% | **8.9%** |
| wait | 21.9% | 23.0% |
| long_scoreboard（等全局） | 10.4% | **7.2%** |

⇒ **栅栏不是成本，它只是等待显现的地方。真正的成本是「操作数必须经 shared 往返」，
以及每 SM 的 MIO 队列吞吐。** 这也解释了**加 block 为何无效**：MIO 队列是每 SM 共享资源，
加 block 只是对同一队列加压（实测 mio_throttle 随 S 加深从 0.9% 升到 7.1%）。

**顺带结掉一个 E-SELF-07 遗留疑点**：`sectors/request = 17.64 ≈ 16`，正是 16 B/lane 的
理论值（512 B/warp = 16 sectors）⇒ **访存合并是满的**，此前「8.45 偏高、合并可能不佳」是
把粒度读错了，不是缺陷。

### 源码级结构事实（已核实，含一处自我更正）

- `:876` 激活 `ldmatrix_x4(a, as + (16*i+lrow)*LD + kk*16 + lcol)` —— **地址不含 warp 号**，
  8 个 warp 读同一份片段；`:867` 权重切片含 `2*warp`，各 warp 不同。
- 按「4 个 row group × 8 warp 全发」预测 ldsm = **76,677,120**，与实测**精确相等**
  ⇒ `if (i < live)` 被编译器**谓词化而非分支**，4 组 ldmatrix 无论 live 多少都照发。
- **⚠️ 自我更正**：不能把这 8 倍叫「可去掉的浪费」——**每个 warp 必须把操作数放进自己的寄存器
  才能喂自己的 MMA**，shared→寄存器读天生是 per-warp 的。
  真正的杠杆是**让激活绕过 shared、直接从 L2 进寄存器**（屋顶内核正是如此，429.8 GB/s），
  代价是 8 倍 L2 流量，而 L2 已被证明承接得住。

**下一步（结构性改动，非开关）**：激活不入 shared，各 warp 直接 `__ldg` 取 a-fragment；
权重仍走 shared（trellis 解码需要）。预期把 short_scoreboard/mio_throttle 大幅压低。
**这是真正的内核重构，需先过精度闸，且 mma2 仍不能跑 TP2 本地 N=1152。**

## 5. 对「吃满硬件」目标的直接回答

**没吃满，而且现在知道差多少、差在哪：**
- DRAM：mma2 达成 ~163 GB/s，机器对同一字节能跑 253.7 GB/s（权重口径）
- 完整 staged 字节口径：mma2 300 GB/s vs 可达 429.8 GB/s ⇒ **效率 70%，还有 1.43× 空间**
- Tensor pipe 48%、SM 50%、L2 25%、L1TEX 21% —— **无一饱和**
- 若把 staging 往返的 6.06 ms 压掉一半，gate/up 单核 22.70 → 19.7 ms（−13%），
  按 Amdahl（底 2084.42、窗口 4.972654 s、gate/up 占 1282.39 ms）约 **+3.4% → 2155**。
  **注意：这是单核收益的 Amdahl 上界，不是承诺；且 mma2 仍不能跑我方 TP2 本地 N=1152。**

## 6. 边界

- 全部离线单核、空载单流；**未在生产多路（head 4.8 GiB）复验**。
- N=2304 全宽（mma2 硬约束 `N%256`），**非我方 TP2 生产形状**。
- **ncu 的 `gpu__time_duration` 在跨流水深度比较时失真**：S=3 在 ncu 下慢 11%，在 event 下快 1.3%。
  **时长一律以 event 为准，ncu 只取计数器**（见手册 §7.13）。
- MODE 1/2/3 的输出故意不完整，**只看时长与计数器，不做数值断言**。
- 改动只在 `exl3src-sweep` 副本与独立产物目录，**未触碰生产源码、未触碰 `exl3src` 原件与 E-SELF-07/08 产物**。
